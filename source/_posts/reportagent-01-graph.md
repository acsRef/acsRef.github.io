## 这个系统在做什么

中文自然语言 → 需求理解 → 补全/确认 → Schema 检索 → SQL 规划/生成/校验/执行/诊断 → 报告。

也就是：**用户说一句话，系统交出一张带数字的表和图，并且这个数字是可被验证的。**

![ReportAgent 两张图](/img/diagrams/agent-graph.svg)

## 一、为什么是两张图，而不是一张大图

一张图走到底最省事，但会让职责糊在一起：什么时候算"理解完了"？出错时是"需求没听懂"还是"SQL 写错了"？

拆成两张图之后，边界很清楚：

| 图 | 职责 | 产出 | 禁止 |
|---|---|---|---|
| **需求图** | 理解意图、识别维度/指标、决定检索、判断缺失、澄清 | `RequirementCard` | 生成/执行 SQL |
| **执行图** | 计划 → 生成 → 校验 → 执行 → 评估 → 诊断/修复 | 查询结果 + 报告版本 | 改需求、编造数据 |

拆开带来三个直接收益：

1. **成本可控**：卡片是唯一执行契约，**用户确认之前不花一次 SQL 成本**；
2. **可观测**：一条链路失败，能立刻判断是"卡没读懂"还是"SQL 写错"；
3. **可重入**：卡改了只需重跑执行图，不用重新理解。

## 二、状态不是一坨 dict

状态拆成五块，各自有唯一写者：

| 块 | 装什么 |
|---|---|
| `RequestState` | 请求级：user/session/原始 query |
| `RequirementState` | 需求级：卡片、草稿、待确认项 |
| `ExecutionState` | 执行级：SQL、结果、评估、重试计数 |
| `ReportState` | 报告级：ReportSpec、版本 |
| `RuntimeState` | 运行级：trace_id、错误、进度 |

为什么要拆：**"谁能写这块"是可检查的**。一旦某段代码需要跨块写，就说明职责画错了。

配套一个真实教训：图上新增状态键必须在 schema 里声明，否则 LangGraph 会**静默丢掉未声明的键**。当时一个 `top_period` 字段死活传不到下游，查了很久才发现是"状态没声明"，而不是逻辑错了。

## 三、六道闸：SQL 不可能"意外伤到库"

生成 SQL 是最危险的一步。校验链从便宜到贵排：

| # | 闸 | 拦什么 |
|---|---|---|
| 1 | 只读检查 | 非 SELECT / WITH…SELECT 一律拒 |
| 2 | 关键字黑名单 | INSERT/UPDATE/DELETE/DROP… |
| 3 | AST 解析（sqlglot） | 顶层必须真的是 Select |
| 4 | 危险函数黑名单 | `pg_read_file` / `dblink` / `pg_sleep` / `set_config` |
| 5 | 表白名单 | 只允许 `dim_*` / `fact_*`；CTE 别名跳过，跨 catalog 拒 |
| 6 | EXPLAIN 真库试跑 | PG 自己说不行就是不行 |

再加一层**数据库层**：分析查询走独立的只读角色（`ragent_readonly`），即使前六道全漏了，DB 也会拒绝写操作。

这个设计的原则是：**不要指望一层拦住所有事，要让漏掉的那一层由下一层兜住。**

## 四、三态落库：可以不成功，但不能假装成功

SQL 执行有三种结果，而且**三种都要落库**：

| 状态 | 含义 | 落什么 |
|---|---|---|
| `SUCCESS` | 有结果行 | 报告 + SQL + 行 |
| `EMPTY` | 合法零行（时间范围内真没数据） | 版本 + 空提示 |
| `FAILED` | 执行/校验失败 | 版本 + `error_kind` + **尝试过的 SQL** |

第三行是重点。很多系统在失败时不写库，结果是：

- 前端只能"转圈到超时"；
- 排查时不知道模型生成了什么 SQL；
- 失败对用户不可见，看起来像卡了。

所以这里明确：**失败也是一等公民，也要留下证据。**

## 五、错误分类：Agent 侧和用户侧是两张表

同一个错误，对 Agent 是"可以修"，对用户可能是"别试了"。所以两张表：

| 错误 | Agent 侧（是否重试） | 用户侧（能不能重试） |
|---|---|---|
| 语法错 / 列名错 | 可以修（重生成） | 提示重试 |
| 权限不足 | 不修（修不好） | 别试了 |
| 超时 | 不修 | 建议缩小范围 |
| 注入 | 拦截 | 拒绝 |

重试预算是写死的：SQL 修复 2 次、MCP 2 次、LLM 2 次。**不允许无限重试**——无限重试等于把偶发错误变成常态成本。

## 六、前端契约：七个事件

SSE 只有七类事件：`phase` / `requirement` / `trace` / `thinking` / `report` / `error` / `done`。

这样前端的状态机是闭合的：任何一个事件都能落到一个明确的状态转移，不需要"猜后端现在到哪了"。断连也不等于失败——任务继续跑完并落库，前端重新连上后靠会话快照恢复真实状态。

## 小结

这一篇的三件事：**拆职责（两张图）、拆状态（五块）、拆失败（三态）**。

它们单独看都不惊艳，但组合起来的效果是：这个系统出的任何一个数字，都能倒查回"哪张卡、哪条 SQL、哪次执行"。这是后面做评测的前提——**不可追溯的系统，没法评测，只能凭感觉。**
