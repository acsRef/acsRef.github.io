## 先说结论

RAG 的效果上限，**在摄入阶段就已经决定**。检索做得再花哨，如果切出来的块本身不自包含，召回回来的就是一堆孤立数字。

所以这一篇讲的是 RAGent（`ragent-py`）的摄入侧：解析 → 清洗 → 结构化 → 切分 → 元数据 → 索引，以及一条被反复验证过的主线——**切分不是切字符串，是保住语义单元**。

![RAGent 摄入管线](/img/diagrams/rag-ingest.svg)

## 一、为什么"按长度切"一定会失败

早期最省事的做法是固定 512 字符切一刀。它在两类内容上立刻崩掉：

1. **表格**：一刀切在中间，列头在上一块、数据在下一块。检索命中的是"1000 亿元"，但不知道这是谁的、哪一年的。
2. **代码/图纸说明**：切口位置随机，语义被腰斩。

所以项目里的切分器按**标题层级（H3/H2）做语义切分**，同时把两类东西标成"原子块"（`is_atomic`）：表格与代码整体不拆。块超限时不硬切，先做**边界装箱**（把相邻小元素塞进同一块），真的还超才做文本级硬切，并保留 64 字符重叠窗口。

这个顺序很重要：**先保住语义，再考虑长度**；反过来就保不住了。

## 二、表格双表示：一份给生成，一份给检索

这是摄入侧最有价值的一个设计，也是踩坑最多的地方。

表格被切碎后最大的问题是**"列-值对应关系"丢失**。原始 Markdown 表格是这样的：

```
| 年度 | 营业收入 | 净利润 |
| 2023 | 1000 亿  | 120 亿 |
```

把这一块拿去做 embedding，向量里混着表头和数据，召回结果往往"看起来相关"但答不对。更糟的是当模型只拿到一行数据时，它不知道 1000 亿是营业收入还是净利润。

解决办法是**一个 chunk 存两份文本**：

| 字段 | 内容 | 用途 |
|---|---|---|
| `chunks.text` | 原始 Markdown，保留列头与版式 | **生成**用：模型能看到完整结构 |
| `retrieval_text` | 逐行归一化成自包含句：「2023 年 营业收入 1000 亿」 | **检索**用：embedding 只吃语义完整的句子 |

配套落库 `chunk_type / table_headers / table_meta`，让下游知道"这块是表格"。

一句话：**同一份内容，给检索看的形式和给生成看的形式，本来就该不一样。** 强行用一份文本兼顾两件事，两边都会将就。

## 三、候选问题通道：摄入期就替用户想一遍"这段能回答什么"

传统 RAG 只有"文档块 ↔ 查询"一个匹配面。但用户的问法常常和文档措辞差很远——文档写"主要会计数据"，用户问"去年赚了多少"。

所以摄入期为每个 chunk 生成候选问题，独立做 embedding，查询期作为**第三条召回通道**参与融合（下一篇详述）。代价是摄入期多一次 LLM 调用，收益是把"问法与措辞不一致"这一整类失败提前消掉。

它的融合权重被压到 0.15——**低权重**是刻意的：问题通道擅长补漏，不擅长主导排序，权重给大了会用"相似的问题"压掉"正确的事实"。

## 四、增量更新：内容 hash 复用

全量重索引在真实知识库上是不可接受的（一次几十分钟，还要重新烧 embedding 和 LLM 元数据）。所以按内容 hash 做复用：

- 未变更的 chunk：直接复用旧 embedding 与 LLM 元数据，不重新调用；
- `embedding` 部分失败的 chunk：**保留旧索引**，标记可重试，而不是把整批写坏；
- 重索引后跑 `tools/index_integrity_report.py` 做硬断言：文档数 / chunk 数 / 问题覆盖率，不达标直接 FAIL。

最后这条是血泪：项目里出现过两次"配置与数据错配"（新配置跑了但索引还是旧的），表现是"检索质量莫名下降"，靠人眼看日志根本发现不了。**指数级难查的问题，用一行断言解决。**

## 五、元数据：批量 + 重试 + 降级不丢块

每个 chunk 要生成结构化元数据（主题、实体、时间等）。实现细节：

- 25 个 chunk 一批，批内失败重试，**重试仍失败则降级**（该块少元数据但保留）；
- 原则：**元数据是增强，不是前置条件**。绝不能因为 LLM 超时就把文档块丢掉——丢块等于永久丢失召回。

## 六、这一层的量化结果

| 指标 | 值 |
|---|---|
| 代码规模 | 25,479 行 Python（其中 8,245 行测试） |
| 测试函数 | 506 |
| 设计文档 | 59 份（每份带「明确不做」） |
| 支持格式 | PDF / DOCX / PPTX / XLSX / HTML / TXT / MD / 图片（Docling + 视觉模型） |

## 小结

摄入侧只有三件事值得投入：**保住语义单元、给检索和生成各一份合适的表示、让重跑是安全的**。其余都是工程细节。
