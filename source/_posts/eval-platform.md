我手上有两个项目：ReportAgent（Agent Runtime）和 ragent-py（RAG Runtime）。它们各自都有评测：
一个 21 条行为期望用例，一个 65 道三一重工年报题（带金标文档 id 和人工核验标记）。

但我一直答不好一个问题：**「你说的这个 74.4%，是什么档位的证据？」**

Demo 跑通、PoC 单次验证、固定 commit + 固定数据集的可复算结果、真实用户受限试行、线上 SLO——
这五个词在 JD 里是一句话，落到工程上是五套纪律。于是我干脆搭了个小平台，把这条纪律钉进代码里。

## 一、平台的形状

一个独立的 FastAPI + 单页前端（`:8200`），**只读**消费两个项目的资产和公开接口，不 import 它们的代码：

```
eval_platform/
├── registry.py    # 两项目用例归一 + 资产登记（来源/覆盖/版本/证据档位）
├── runners.py     # 三层判定：deterministic / gold / deferred
├── scenarios.py   # 场景测试：增量更新 / 删除 / 跨库隔离
├── adapters.py    # HTTP 适配（两个服务各有自己的 venv）
├── store.py       # SQLite：每次运行的环境指纹 + 结果
└── static/        # 单页 UI（无构建、无依赖）
```

六个页面直接对应 JD 的每一条：总览（被测对象 + 版本 + 覆盖）、实时测试（逐条 check）、
资产（来源/覆盖/版本/复用/档位）、场景测试（小功能与细节）、风险库（五类边界案例）、
方法（方法论 / 资产登记 / 风险库 / 证据分量 四份文档）。

## 二、判定分三层，`deferred` 不给分

这是整个平台唯一值得信的地方：

| 层 | 判什么 | 进 pass 率 |
|---|---|---|
| `deterministic` | 字段、集合、命中，可离线复算 | ✅ |
| `gold` | 金标比对（现跑 SQL / 现查 doc_id / 关键词） | ✅ |
| `deferred` | 本轮没覆盖的层（执行层要 confirm、生成层要裁判） | ❌ 页面显式标注 |

比如 ReportAgent 的用例跑完之后，需求卡字段是 pass，但「执行 / 报告」两层会亮成
`deferred`——**不是通过，是没测**。宁可难看，也不给假 pass。

## 三、真机跑出来的四个坑

平台写完，真跑一遍才发现「看着能跑」有多不可靠：

**① `/api/v1/chat` 要 JWT。** 我按「公开接口」写的适配器，第一次跑就 422：`missing authorization`。

**② SSE 帧是 CRLF 分隔的。** 我按 `\n\n` 切帧，结果整条流被当成一帧，只解析出最后一个 `done`——
需求卡永远是空。真机日志里 30 个事件，我只拿到 1 个。

**③ 按行 break 会切在 `event:` 和 `data:` 之间。** 修了 ② 之后仍然失败：我为了省时间在读到
`event: requirement` 时中断读取，结果那一帧的 data 还没来。改成整条流读完再解析。

**④ 指标匹配用子串，会把「净销售额」当成「销售额」。** 这是最讽刺的一条：我自己的风险库里
第一条风险就是「口径被换」（RA-R1），结果平台的判定器差点把它判成 pass。改成归一后**等值**比较。

## 四、资产重挂：金标文档 id 会漂

RAG 那 65 道题的金标是 `gold_documents`（document_id）。第一次跑 Q01 全红，我以为检索坏了；
查库才发现：金标 id 是 **2026-08 首次入库**时的，2026-11 三份年报重新入库后 id 全变了：

| 旧金标 id | 年份 | 当前 document_id |
|---|---|---|
| `c70a…` | 2023 | `e15c045948484d58` |
| `f4b0…` | 2024 | `61be97f9c87742f5` |
| `aebd…` | 2025 | `a005c3a33dea4d2a` |

不重挂，`doc_hit@5` 就是**全量假失败**。平台的处理不是把新 id 写死在代码里，而是维护一张
`rag_doc_map.json`：比对前先映射，页面注明「已按 rag_doc_map 重挂」。

> 这条比任何指标都重要：**资产和环境是有版本的**。重入库、换 embedding 模型、删库，都要重建映射表。

## 五、场景测试：测「小功能」和细节

单条用例回答「这条 query 命中了吗」；场景回答工程问题。这三个场景都是**会改数据**的，
所以每个都自建临时知识库（`eval-tmp-*`）、跑完删干净，绝不碰生产库：

| 场景 | 关键断言 | 实测 |
|---|---|---|
| 增量更新（同一 document_id 覆盖） | 文档数不增长；新内容可召回；**旧内容不再召回** | ✅ 297s，文档数 1，旧 token 消失 |
| 删除后无脏召回 | 列表清空；再检索不返回该文档 | ✅ 153s |
| 跨库隔离（pin kb_ids） | 生产库检索不返回临时库文档 | ✅ 146s |

第一次跑这三个**全是 fail**。原因不是产品坏了，是我的等待上限设了 90 秒——
而一份 3 行 markdown 从上传到 `indexed`，实测要 **141 秒**（分块 + embedding）。

这就是「证据分量」的现实版本：**工具超时 ≠ 产品失败**。所以现在把入库超时单独记成 `timeout`，
verdict 记为 `error`（既不是 pass 也不是 fail），并在说明里写清「工具上限，不代表产品失败」。

## 五·五、评测工具自己也会造成事故

这篇最该留档的一段：**我的清理逻辑把 ragent 的文档库删光了。**

平台跑场景时会建临时知识库，跑完删掉。我写的是「按 kb 列文档 → 逐个删」。
但 `GET /api/v1/documents` **不接受 `kb_id` 参数**（签名只有 limit/offset），admin 拿到的是全库——
于是"删临时库的文档"变成了删 14 份文档 / 1391 个 chunk（三一年报 + 数据字典 + FAQ）。

更糟的是我没第一时间发现：第一次跑场景时它报「文档数=16（期望 1）」——**那条断言就是事故本身**，
我却把它当成"入库未就绪"的噪音，继续去调等待上限。教训：**当数字差一个数量级时，先查作用域**。

修复三件事：

1. `ragent_docs(kb_id)` 改成**客户端过滤**（只收 `kb_id` 匹配的），并把这个理由写进 docstring；
2. 清理只作用于"本库的 document_id"；
3. 加一条回归测试：构造一条别库文档，断言它不会出现在本库列表里。

恢复走项目自带的灌库路径，不手改数据库：数据字典用 `mcp_server` 的 `ingest_table_schemas`
（自省 PG → render → upload），FAQ 用 `ingest_faq`（20 条 seed），三份年报重传 PDF。
恢复完 document_id 会变——所以「资产重挂」那一节不是理论，是每次重建后必须做的动作。

> 评测工具和生产代码一样需要「作用域断言」和「破坏性动作先 dry-run」。这条我记在自己的风险库里（EV-R1）。

## 六、把结论钉在环境上

每条运行记录都落 SQLite：`base_url`、两个项目的 commit、资产清单、判定层、证据档位、延迟。
页面「历史」里点开就能看到——回答「这条结论在什么环境、什么版本、覆盖了哪几层」。

配套四份文档（平台「方法」页原样渲染）：

- `methodology.md`：五要素模板、指标口径、三层判定、失败归因（oracle / capability / contract / environment / flaky）；
- `asset-registry.md`：每份资产的来源、覆盖、版本、复用方式、档位，以及上面那节「资产重挂」；
- `risk-case-library.md`：误答 / 幻觉 / 越权 / 错误执行 / 不可追溯，RA 五条真实事故 + ragent 从题目元数据自动派生；
- `evidence-weights.md`：Demo → PoC → 测试环境 → 受限试行 → 正式运行，每档「允许说什么、禁止说什么」。

## 八、一句话

评测平台的价值不在于「能跑」，而在于**它替你说了那些不好听的话**：

> 这一层没测（deferred）；这个结论只到测试环境；金标已经漂了要重挂；超时是工具的锅不是产品的。

这些话写在文档里会被人忽略，写进代码里就成了门禁。
