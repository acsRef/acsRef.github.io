## 问题：两条记忆像不像，谁说了算？

系统里会同时存在这样的两条记忆：

```
A: 以后都用柱状图
B: 以后报告默认给柱状图
```

和这样的两条：

```
A: 以后都用柱状图
B: 以后不要用柱状图
```

第一组应该合并（同一件事的两种说法）。第二组**绝对不能合并**（语义相反）。

而它们的字面相似度几乎一样高。这就是记忆归并的全部难点：**"像"不等于"是同一件事"**。

这篇讲三件事：我怎么量它、量出了什么、最后怎么判。

---

## 一、先量，再设计

我最初的方案非常自然：**用 embedding 余弦相似度自动合并，相似度超过阈值就并。**

动手之前我做了个探针：26 对样本，人工标注三类关系——

| 标签 | 含义 | 对数 |
|---|---|---|
| `merge` | 同一件事的两种说法，该合并 | 12 |
| `distinct` | 不同维度 / 不同指标，不该合并 | 9 |
| `opposite` | 字面极像但语义相反，绝对不能合并 | 5 |

用真 embedding（Qwen3 系列）算余弦，得到的三类分布：

| 标签 | 最小 | 中位 | 最大 |
|---|---|---|---|
| `merge`（该并） | 0.694 | 0.881 | 0.933 |
| `distinct`（不该并） | 0.642 | 0.809 | **0.950** |
| `opposite`（绝不能并） | **0.906** | 0.933 | **0.962** |

**三类完全重叠。** 最刺眼的一行是最后一行：**"相反说法"的下界（0.906）比"同义"的中位（0.881）还高。**

也就是说：如果你把阈值定在 0.90，你会把大量"相反说法"合并掉——这是记忆系统里最坏的错误，因为合并之后旧值会被覆盖，**用户说的"不要"会变成"要"**。

阈值扫描更绝望：

| θ | 误并 | 误拆 |
|---|---|---|
| 0.80 | **11** | 2 |
| 0.90 | 7 | 8 |
| 0.94 | 3 | 12 |

**没有一个阈值能用。** 不是参数没调好，是这个信号本身不够——它对"语义相反"几乎不敏感（否定词只改一两个字，向量几乎不变）。

---

## 二、改用结构判定

结论：**先从文本里抽"结构原子"，用原子比较决定关系；余弦只用来决定"要不要送人工复审"。**

![判定流程](/img/diagrams/merge-decision.svg)

判定顺序（每一步都是确定性的）：

```
① 极性一致？   一条有否定词、另一条没有 → distinct
② 数字相同？   抽出的数字集合不同        → distinct
③ 原子冲突？   图表/粒度/区域/指标任一不同 → distinct（并指出是哪个原子）
④ 原子完全相同？ 同类型、同取值、非空     → merge（累加证据）
⑤ 否则：余弦 ≥ 0.90 → review（只记待复审，不自动合并）
        否则        → distinct
```

原子长什么样（真实输出）：

| 文本 | 抽出的原子 |
|---|---|
| `以后都用柱状图` | `{chart: [bar]}` |
| `以后不要用柱状图` | `{chart: [bar]}` ← **原子相同！** |
| `净销售额包含退款` | `{metric: [净销售额]}` |
| `净销售额不包含退款` | `{metric: [净销售额]}` ← **原子也相同！** |

注意这两组：**原子完全一样，只有极性不同。** 所以第 ① 步（极性）必须先做——如果只比原子，这两组会被判成"完全一致"然后合并，那就是灾难。

这就是为什么判定顺序不能变：**先去极性，再去数字，最后才比原子。**

两个数字里，**我最在意的是"误并 = 0"**。原因：

- 误并的后果是**静默的数据损坏**（旧值被覆盖、相反偏好被当成同义），用户永远不知道；
- 漏并的后果只是"多存一行"，最多多一次复审。

所以这个判定器是**故意偏向保守**的。

## 四、两处漏并，根因是同一个

**漏并 #9**：`GMV 按净销售额算` / `GMV 就是扣掉退款之后的销售额`

| 文本 | 抽出的指标原子 |
|---|---|
| A | `{净销售额}` |
| B | `{销售额}` |

B 那句话**没用术语**（说的是"扣掉退款之后的销售额"），所以匹配到的是泛词「销售额」；A 里「净销售额」更长，覆盖了「GMV」。两条明明在说同一件事，原子却不同 → 判 distinct。

这是**语义能力问题**，结构判定解决不了（除非上模型判断，那就回到不确定）。

**漏并 #11**：`退货率按订单数算` / `退货率的分母用订单数量`

| 文本 | 抽出的指标原子 | 为什么 |
|---|---|---|
| A | `{退款率, 订单数}` | 「退货率」= 退款率（3 字）、「订单数」（3 字），都留下 |
| B | `{订单数}` | 「订单数量」（4 字）压掉了「退货率」（3 字） |

这是**"最长命中优先"跨指标比较**带来的 bug：B 里「订单数量」比「退货率」长，于是只保留了订单数，把退款率丢了。

有意思的是：**同一个根因，我在检索路径上也修过一次**（"销售额和退货金额对比"只留下"退款金额"）。但归并这边我**没修**，理由是：

1. `metrics_mentioned_in` 在这里的语义是"这段话围绕哪个口径"，单主题更合适；
2. 这里失败方向保守（漏并 ≠ 错并）；
3. 要改它得连带评估另一个消费方（SQL 提示词里的口径白名单）。

**知道 bug 在哪、评估完影响、然后决定不修**——这也是工程判断的一部分。

## 五、判定器之外：真正保证一致性的是存储

即使判定器全对，也只是"识别"；**"不冲突"是靠存储结构保证的**：

```
唯一键 = (user_id, memory_key)
memory_key 是意图槽位：pref:chart / pref:chart:exclude / pref:granularity / fact:<指纹>
```

- 同一维度只有**一行** → 物理上不可能存在两条矛盾偏好；
- 冲突写法走 **UPSERT 覆盖**（`revision+1`，旧值留在 `previous_content`）；
- 否定单独一个槽（`pref:chart:exclude`）→ 「不要柱状图」永远不会覆盖「用饼图」。

再加两条治理规则：

| 规则 | 目的 |
|---|---|
| 同一说法观察到 ≥3 次才晋级 active，confidence **封顶 medium** | 推断不等于事实；`high` 只留给用户明说 |
| 判定移出热路径（每日跑批 + `promoted_at` 幂等） | 在线只读写，不做判定，成本与延迟可控 |

## 六、三条可复用的经验

1. **用相似度做判断前，先去量"你不想合并的那类东西"的相似度。** 如果两者重叠，换信号，别调阈值。
2. **判定顺序比判定规则更重要。** 极性必须在原子之前——否则"包含/不包含"会被判成一致。
3. **失败方向要选。** 这个场景里漏并远好于错并，所以所有"拿不准"都倒向 distinct / review。
