## 链路长什么样

![RAGent 检索链路](/img/diagrams/rag-retrieval.svg)

一句话概括：**query 改写 → 意图路由 → 三路召回 → RRF 融合 → 跨编码器精排 → MMR 去冗余 → 证据组装 → 流式生成**。

## 一、为什么要三路召回

单靠向量检索会在两类查询上翻车：

| 查询类型 | 例子 | 向量的问题 | 谁来补 |
|---|---|---|---|
| 精确字面匹配 | 「研发投入情况表」 | 语义被"平均"掉了，专有表名召不回 | BM25（jieba + PG ts_rank） |
| 问法与措辞差异 | 「去年赚了多少」 | 与"主要会计数据"距离远 | 候选问题通道 |

三路各有明确职责，所以是**并列召回 + 融合**，而不是串行"一个不行再试下一个"。

两个细节：

- **BM25 用 OR 语义**（`OR-tsquery`），召回不足 `top_k` 时再 relaxed 兜底。用 AND 会在长查询上直接归零。
- **问题通道权重 0.15**。低权重是设计：它擅长补漏，权重给大了会用"相似问题"压掉"正确事实"。

## 二、RRF：按排名融合，不按分数

三路的分数量纲完全不可比——向量是余弦相似度（0~1），BM25 是无上界的 tf-idf 加权和，问题通道又是另一套。

所以用 **RRF（Reciprocal Rank Fusion）**：只看排名，不看分数。

```
score(d) = Σ_channel  1 / (k + rank_channel(d))
```

工程收益很直接：**换 embedding 模型、调 BM25 参数，都不需要重新调融合权重**。融合层因此变成了"无参数"的，这在多路系统里是非常值钱的稳定性。

## 三、精排与去冗余

- **跨编码器精排**：`bge-reranker-v2-m3`，把 query 与候选块拼起来过一次模型，比向量内积准得多；
- **MMR 去冗余**：λ=0.7，每个文档最多 2 块，跨文档软约束。

为什么必须去冗余：年报里同一句话往往在"管理层讨论"和"财务报表附注"里各出现一次。只做相关性排序会把同一个事实取两遍，**看起来证据充分，实际信息量没变**，还挤掉了本可以进入上下文的其它事实。

## 四、消融：8 组配置，召回增益为 0

这是整个项目里我印象最深的一次实验。为了提升跨文档问答和错误前提纠偏的准确率，我实现了 5 个检索策略：

1. 跨文档关联检索（摄入期预建 TF-IDF 关系边）
2. 权威 section 加权（财务关键词触发）
3. 权威 section 定向补充
4. 跨年覆盖补充
5. 复杂查询拆解

然后跑了 8 组 retrieval-only 消融（20 题回归集，每次只开一个策略）：

| # | 配置 | hit@5 | hit@10 | recall@10 | MRR | 延迟 |
|---|---|---|---|---|---|---|
| 1 | Baseline（全关） | 0.95 | **1.000** | 1.000 | 0.842 | 670 ms |
| 2 | 5 策略全开 | 0.95 | **1.000** | 1.000 | **0.850** | 580 ms |
| 3 | 仅跨文档 | 0.95 | **1.000** | 1.000 | 0.850 | 567 ms |
| 4 | 仅 section 加权 | 0.95 | **1.000** | 1.000 | 0.850 | 570 ms |
| 5 | 仅 section 补充 | 0.95 | **1.000** | 1.000 | 0.850 | 568 ms |
| 6 | 仅跨年补充 | 0.95 | **1.000** | 1.000 | 0.850 | 660 ms |
| 7 | 仅 Evidence Gate (.7) | 0.95 | **1.000** | 1.000 | 0.850 | 596 ms |
| 8 | 仅 Evidence Gate (.5) | 0.95 | **1.000** | 1.000 | 0.850 | 589 ms |

**hit@10 在 8 组里全部等于 1.000。** MRR 从 0.842 到 0.850，+0.8pp——在重排模型噪声范围内。延迟 567–670ms，策略 hook 几乎不影响耗时。

结论不是我想要的那个：**这一层的检索已经到天花板了，我加的所有策略都没有价值。**

## 五、比"没提升"更重要的三个判断

**① 把"没有增益"当成结论，而不是当成失败去掩饰。**
这些策略的代码全部保留（可作为单点复评的开关），但**默认关闭、不进生产**。理由写成了一行注释留在配置里：`Retrieval strategies default off: 8-group ablation showed no recall gain`。

**② 真正的增益在别处。**
同一时期真正有效的是"**权威表格定向补充**"：财务表格在 BM25 里得分低，常被挤出 top-K。做法是 query 含财务词时，额外对权威 section 做一次 BM25，并对已在主检索里的权威块 ×3.0 加分。效果：

| 题型 | 改前 | 改后 |
|---|---|---|
| A 类（单文档事实） | 56.7% | **83.3%**（+26.6pp） |
| B 类（表格理解） | 61.1% | **94.4%**（+33.3pp） |

**③ 消融还顺带暴露了一个方法论陷阱：评测路径 ≠ 生产路径。**
`/api/v1/retrieve` 端点**绕过**了 pipeline 里的 evidence gate，而生产 chat 走的是 `/chat/stream`。也就是说那 8 组里两行"Evidence Gate"的数值，测的根本不是 gate 生效的路径。发现之后，Evidence Gate 的评估单独改走 generation 评测（65 题 × 4 配置）。

这个坑很典型：**你以为在测 A，其实测的是 A 的近似物。** 任何"评测脚本直接调内部函数"的做法，都有这个风险。

## 六、还保留着什么

| 能力 | 状态 |
|---|---|
| 三路召回 + RRF | 始终开启 |
| 跨编码器精排 | 始终开启（失败降级为跳过） |
| MMR | 始终开启 |
| 检索缓存 / 熔断 / 降级提示 | 始终开启 |
| 5 个高级策略 / Evidence Gate | 代码保留，**默认关闭** |

## 小结

检索层的正确姿势是：**先把基础三件套做扎实（混合召回 + 精排 + 去冗余），然后用消融诚实地验证每一个"聪明想法"。**

大多数"高级检索范式"在中文长文档语料上带来的不是召回，而是复杂度。
