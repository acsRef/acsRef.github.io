前两篇讲"怎么取到对的材料"，这一篇讲"怎么证明它是对的、出错时怎么兜、以及怎么被别的系统用"。

## 一、评测系统：两层门禁 + 唯一数据入口

评测混乱的根源通常不是"没有指标"，而是**指标和数据集各有各的入口**，跑三次得三个数。

所以第一件事是收口：所有评测集只允许通过 `eval/gold.py` 读取，带 schema 校验与自检（`self-check`）。任何脚本绕过它直接读 JSON 都会被这一层挡住。

然后是两层：

| 层 | 规模 | 用途 | 触发 |
|---|---|---|---|
| **Verified regression gate** | 15 题 | 改动前后**不许退化** | 每次改动 |
| **正式 benchmark** | 65 题 | 看绝对水平、做消融 | 里程碑 |

15 题那层的关键是**快**：能在一次改动后几分钟内给出"有没有变差"，而不是等一小时的全量评测。全量评测只在需要看绝对水平时跑。

### judge 的三个细节

用 LLM 当裁判最容易糊弄自己，所以规则写死在 `judge_rubric.py` 里：

1. **3 分制**，每档有明确的文字标准（不是让模型"给个 1-10 分"）；
2. **错误拒答判 0 分**——拒答在 RAG 里是最危险的"看起来安全"的行为：检索到证据却拒答，比答错更难被发现；
3. **确定性数字校验辅助**：B 类（表格理解）这类问题，数字对不对可以直接比对，不需要 judge 参与。

第 3 条是最省心的一条经验：**能用确定性方法判的，绝不给 judge。** judge 只处理"表述是否切题"这种真正需要语义判断的部分。

## 二、PII：三层检测，而不是一个正则

一行正则会在真实数据上被三种情况打穿：格式变体、校验位错误（假号码）、以及**上下文否定**（"示例：138xxxx"里的号码不该拦）。

所以做三层：

| 层 | 做法 | 拦什么 |
|---|---|---|
| 1 | 正则 | 明显格式：身份证/手机/邮箱/银行卡 |
| 2 | 算法校验：Luhn（银行卡）/ mod-11（身份证） | 格式对但校验位错的假号码 |
| 3 | 上下文排除 | 示例、占位符、测试数据 |

命中后二选一：**脱敏**或**拒审**；管理员可审核（确认 / 误报 / 白名单）。白名单这一步是必要的——纯自动化的 PII 检测在生产里一定会误杀，没有申诉通道就没人敢用。

## 三、权限：8 项权限 + 三级可见性

| 维度 | 取值 |
|---|---|
| 权限 | `chat` / `doc.upload` / `doc.read_all` / `kb.create` / `kb.delete` / `kb.manage_visibility` / `user.manage` / `admin` |
| 知识库可见性 | `public` / `internal` / `restricted` |

要点是**"能看文档"与"能看全部文档"分开**（`doc.upload` vs `doc.read_all`），以及**可见性单独授权**（`kb.manage_visibility`）——不然任何能建库的人都能把自己的库设成 public。

## 四、降级：区分"故障"与"没有内容"

RAG 的失败面比普通接口宽：向量服务挂了、重排模型超时、数据库抖动、以及**真的没有相关资料**。这四种如果都回同一个"抱歉没找到"，用户和运维都会懵。

所以做了分流：

| 情况 | 表现 |
|---|---|
| 向量/重排失败（5xx、429） | 自动降级：BM25-only / 跳过重排 / 备用响应，并在流里推 `degraded` 事件 |
| 数据库故障 | 明确的错误事件（不是"没找到"） |
| 真的没检索到 | `no_context` 事件 + 明确话术 |

配套**按 provider 隔离的熔断器**：一个 provider 挂了不该把整条链路拖死。

还有一条容易忘的：**思考流与回答流分开推**（`thinking` / `token`），由 `tag_parser.py` 统一解析模型的 think 标签。这一层是纯逻辑，12+ 个单测覆盖——因为它是"看起来能跑、错起来很难查"的典型位置。

## 五、可观测性：把每次查询的链路存成 JSON

每次查询都会落一份诊断 JSON：

```
rewrite → intent → retrieve → rerank → mmr → stream
```

每个阶段带输入输出摘要、耗时、命中数。前端有对应页面可以直接看"这一次为什么召回了这几块"。

这一层的价值在排查时体现：用户说"答得不对"，你能在一分钟内回答"是没召回到、还是召回到了但排序压掉了、还是召回到了但模型没用"。**没有这三个区分，所有问题都只能靠猜。**

## 六、MCP：把自己变成别人的工具

RAGent 里有一个独立进程 `mcp_server/`，做的是**数据字典服务**：

```
PG 自省 → 确定性 Markdown 渲染 → 上传到本系统 KB → 对外暴露检索工具
```

它通过 MCP（stdio）对外提供 `search_faq`、`search_tables` 这类工具。这样另一个项目（ReportAgent，SQL Agent）需要"业务口径 FAQ / 表结构"时，**不需要自己实现 embedding / 向量检索 / 重排**，直接调工具即可。

这条边界是刻意画的：

| 归 RAG Runtime | 归 Agent Runtime |
|---|---|
| 解析、切分、索引、召回、重排 | 需求理解、SQL 规划、执行、报告 |
| "把资料找出来" | "决定下一步做什么" |

一句话：**Agent 不应该重建索引，RAG 也不应该长出 Agent 循环。**

## 七、这一层的量化结果

| 项 | 值 |
|---|---|
| 提交 | 223 次（2026-06-17 → 2026-09-08） |
| 代码 | 25,479 行 Python（8,245 行测试，506 个测试函数） |
| 设计文档 | 59 份 |
| 评测 | 15 题门禁 + 65 题基准；retrieval hit@10 = 1.000，MRR ≈ 0.85 |

## 小结

这一篇没有"高级技巧"，全是让系统**可被信任**的东西：唯一的评测入口、确定性优先的评判、能申诉的安全策略、区分故障与空结果的降级、能把"为什么"讲清的可观测性、以及一条干净的对外边界。

这些东西不会让 demo 更惊艳，但决定它能不能被第二个人接手。
