## 为什么不是一个大项目

最省事的做法是把 RAG 塞进 Agent 里：反正都要调 LLM，反正都要向量库。但这个选择会让后面每一步都变贵：

- **迭代耦合**：换 embedding 模型要动 Agent 的代码，改 SQL 提示词又要担心索引；
- **职责糊掉**：出问题时说不清是"没检索到"还是"Agent 没用对材料"；
- **无法独立评测**：RAG 的召回指标和 Agent 的任务成功率混在一起，谁都说不清改动有没有用。

所以拆成两个项目，各自是一个可独立运行的 Runtime：

![两个 Runtime 与 MCP 边界](/img/diagrams/overview.svg)

| | RAGent | ReportAgent |
|---|---|---|
| 定位 | **检索运行时** | **Agent 运行时** |
| 输入 | 文档（PDF/Office/图片…） | 一句中文问题 |
| 输出 | 带引用的答案 + 证据块 | 一张带数字的表和图 |
| 核心资产 | 索引、召回、重排 | 需求卡、SQL、报告版本 |
| 独立评测 | hit@k / recall@k / MRR | 执行准确率 / 分档 / 子任务归因 |

## 边界是怎么画的

一句话：**RAG 负责"把资料找出来"，Agent 负责"决定下一步做什么"。**

具体到能力上：

| 只在 RAGent 里 | 只在 ReportAgent 里 |
|---|---|
| 多格式解析、清洗、切分 | 需求理解、澄清、需求卡 |
| embedding、向量索引、BM25 索引 | SQL 计划 / 生成 / 校验 / 修复 |
| 三路召回、RRF、重排、MMR | 执行、三态评估、报告生成 |
| 引用与证据组装 | 报告版本、记忆、trace |

两条否定式约束比正面清单更重要：

- **Agent 不得重新实现 embedding / 分块 / 向量检索 / 重排**——它只能通过 MCP 使用；
- **RAG 不得长出 Agent 循环**——它不决定"下一步查什么"，只回答"这些材料里有什么"。

第二条常被忽略。RAG 系统很容易滑向"多轮检索 Agent"（自己规划检索路径、自我反思），一旦滑过去，两个项目的边界就没了，评测也会失去意义。

## 那条边界长什么样：MCP

RAGent 里有一个独立进程 `mcp_server/`，做的是**数据字典服务**：

```
PG 自省 → 确定性 Markdown 渲染 → 上传到本系统 KB → 通过 MCP 暴露工具
```

对外的工具很短：`search_faq`（业务口径、指标定义）和 `search_tables`（表结构）。

ReportAgent 侧用 stdio 方式连上它，把工具注册进自己的工具注册表，然后在 SQL 规划阶段调用——于是"指标口径"这种知识**不需要写进 Agent 的 prompt，也不需要 Agent 自己维护向量库**。

这里有一个我觉得比协议本身更重要的设计：**工具失败必须显式说不出来，不许返回空数组假装"没有结果"。**

```
❌ 检索失败 → []
✅ 检索失败 → unavailable / timeout，由上层决定 retry / clarify / fail
```

原因很直接：空数组会被下游当成"知识库里确实没有这条"，于是系统会自信地答一个错的。**伪装的空结果比报错危险得多。**

## 两边共用的三条原则

两个项目加起来 719 次提交、127 + 59 份设计文档，真正沉淀下来的原则只有三条：

**① 确定性优先，模型只处理歧义**

| 位置 | 做法 |
|---|---|
| RAGent 意图识别 | 关键词/规则先判，模型只兜底 |
| RAGent 检索 | 三路召回 + RRF（无参数融合），不靠模型调权重 |
| ReportAgent 意图 | 关键词 → 字典 → 模型兜底；1427 轮里 64% 不调模型 |
| ReportAgent 需求 | 模型产出理解，**代码做裁决**（时间/范围/口径确定性回填） |

**② 错误路径是一等公民**

- ReportAgent：SQL 失败也落一条 `report_version`（带 `error_kind` 与尝试过的 SQL），永不伪造成功；
- RAGent：区分「向量服务挂了」「重排超时」「数据库故障」「真的没检索到」四种情况，四种话术。

**③ 能量化才敢说好**

| 项目 | 数字 |
|---|---|
| RAGent | retrieval hit@10 = **1.000**；MRR 0.842 → 0.850（+0.8pp，噪声内）→ 结论：**高级策略默认关** |
| RAGent | 权威表格定向补充：A 类 56.7% → **83.3%**，B 类 61.1% → **94.4%** |
| ReportAgent | 记忆召回 R@1 **0.840** / R@3 **0.960** / MRR **0.900** |
| ReportAgent | 执行准确率 0 → **10/10**；跑通率 1.0 而答案错 3.4 倍过 |

## 踩过的三个坑

**① 评测路径 ≠ 生产路径。**
RAGent 的 `/api/v1/retrieve` 端点绕过了 pipeline 里的 evidence gate，而生产 chat 走 `/chat/stream`。于是"Evidence Gate 的消融数据"其实测的不是 gate 生效的路径。**任何评测脚本直调内部函数都有这个风险。**

**② 框架会静默丢状态。**
LangGraph 只传递在 schema 里声明过的状态键。一个没声明的字段死活传不下去，查了很久才发现不是逻辑问题。**"没报错但没生效"比报错难查十倍。**

**③ 同一个缺陷要在两条路径各修一遍。**
ReportAgent 里存在两条需求理解流水线（默认路径与开关路径），规则集不同。我用差分探针（同一句话 + 同一份模型输出 → 只比执行契约字段）量出 4 类差异，逐条判定谁对，才收敛成一份实现。

## 一句总结

**两个 Runtime 的价值不在于各自功能多，而在于它们能被分开评测、分开演进，并且在边界上互不解释对方的内部。**
