## 一、指标选错，等于自欺

很长一段时间，这个项目的头号指标是 `sql_success_rate`。它衡量的是：

> SQL 执行成功，并且返回了行。

20 条基线用例全绿。听起来很好。但它衡量的是 **execution success**，不是 **execution accuracy**——一条 SQL 只要跑通且有数据就算过，**算错了也算过**。

这中间的差距有多大？第一次把"结果比对"接上：

```
case: 2024年各区域销售额排名
gold: 华东 96,318,061.74      6 行
pred: 华东 326,102,457.72     6 行
```

**行数一样、列数一样、跑得通、有数据——数字差 3.4 倍。**

## 二、我的第一判断是错的

看到 3.4 倍，我第一反应非常自信：**1:N join 扇出**。

理由看起来充分极了。被测 SQL 长这样：

```sql
SELECT dim_store.region,
       SUM(fact_orders.order_amount) - COALESCE(SUM(fact_payments.payment_amount), 0)
FROM fact_orders
LEFT JOIN dim_store    ON fact_orders.store_id = dim_store.store_id
LEFT JOIN fact_payments ON fact_orders.order_id = fact_payments.order_id
                       AND fact_payments.status = 'REFUNDED'
GROUP BY dim_store.region
```

一个订单有多条退款记录时，`LEFT JOIN` 会把订单行**复制** N 份，`SUM(order_amount)` 就被放大 N 倍。经典的扇出。

我甚至写好了一段解释，准备讲"这就是为什么必须闭环评测"。

**然后我去查了数据。**

| 检查 | 结果 |
|---|---|
| 每单支付条数分布 | **全部 = 1**（179,947 单，无一例外） |
| 每单退款条数分布 | **全部 = 1**（10,600 单） |
| 扇出写法 vs 安全写法（逐区域净额） | 六区域**完全相同** |
| `fact_orders.order_date` 范围 | **2023-01-01 ~ 2026-10-31** |

最后一行是决定性的：**数据是四年，不是一年。** 而金标的 SQL 里有 `WHERE d.year = 2024`。

3.4 倍 = 「四年 ÷ 一年」× 「毛额 vs 净额」。**和扇出一点关系都没有。**

## 三、真因在需求层，而且是两条

继续往下查（查卡片、查任务归并记录、查原话），真因浮出来了：

```
task : {"time_range": null, "metrics": [], "goals":[{"metric":"销售额","dimension":"区域"}]}
card : {"time_range": null, "target_metrics": ["净销售额"]}
sql  : 没有任何时间谓词
```

**① 时间范围丢了。** 模型这一轮没给 `time_range`，而这条路径**没有确定性兜底**。用户明写的「2024年」从未进入 SQL。

**② 口径被改写了。** 模型把口径**正确地**放在了 `goals[0].metric = "销售额"`，但任务的 `metrics` 是空数组 → 系统判定"缺口径"，于是生成候选：

```python
options = sorted(known_metrics)[:3]
```

中文按 Unicode 码点排序，`净`(U+51C0) < `销`(U+9500)。于是候选成了 `净销售额 / 实收金额 / 客单价`——**用户明说的「销售额」被挤出了选项**。评测夹具再"选第一个"，毛额就变成了净额。

两个缺陷是同一类：**模型负责理解，但代码该裁决的地方没有裁决。**

## 四、修法：确定性回填 + 只在留空时

| 位置 | 改动 |
|---|---|
| 时间 | `time_range_from_query()`：`2024年` / `2024年7月` / 闰月区间 / 中文月份 → 卡片值；相对词与裸数字**不猜** |
| 范围 | `scope_from_query()`：复用区域词表，明写「华东」就落位 |
| 口径 | 原话唯一命中 → 落位；命中多个 → **全部保留**（多口径对比不是歧义）；没点名 → 注册表默认 + assumption（不问） |

关键原则：**只在留空时回填，模型给了一律尊重。**

## 五、第二次翻车：回填放错了层

修完单轮就绿了。然后我加了多轮用例，第二次红：

```
turn1 card: 2024年 · 销售额          ✅
turn2 task: {"time_range": null, "metrics": []}   ← 任务仍是空的
turn2 card: 时间空 · 净销售额      ❌ SQL 无年份过滤，金标 1 月 8.99M vs 实测 83.7M
```

原因很朴素：**多轮继承读的是"任务"，我把回填放在了"卡片"上。** 卡片每轮重投影，看起来对；任务才是被继承的东西，一直是空的。

修法是把回填下沉到任务归并（`reduce_task`）里，并**删掉卡层那两个函数**——留着会掩盖任务层的缺陷，而它已经掩盖了一次。

这条经验很硬：**只在单轮验证过的修复，等于没修。**

## 六、金标从 1 条铺到 10 条，每条都在抓 bug

| 覆盖 | 数量 |
|---|---|
| 有金标 | 10 / 20 |
| 没有金标 | 10（澄清类 2、安全 1、闲聊 2、检索 2、故障注入 1、**多解 1**、**明细 1**） |

后面两类是刻意不标的：

- 「再按产品细分」既可读成「月 × 品类」也可读成「换成品类」，**写死一种等于替产品做决定**；
- 明细查询带 `LIMIT 200`，排序并列时行集不确定，金标会随实现漂移。

**覆盖率低但有理由，比 20/20 全绿而理由是"照抄被测 SQL"有价值得多。**

铺金标的过程本身就在抓 bug，一共抓出三个真缺陷：

| case | 现象 | 真因 |
|---|---|---|
| 多轮继承 | 第 2 轮丢 `time_range` | 回填放错层（见上） |
| 单区域月趋势 | 12 行值 ≈ 全国各月（2.66 倍） | `scope` 无确定性兜底 |
| 双口径对比 | 只出 1 列「退款金额」 | 多口径识别只保留最长命中（4 字 > 3 字） |

## 七、再往前一步：分档 + 子任务归因

只有"结果对不对"还不够——它只说"错了"，不说"错在哪"。所以又加了两层：

**复杂度分档**（从金标结构推导，不人标）：T1 单表 / T2 星型 join / T3 预聚合·多口径·明细。

**子任务诊断**：把金标 SQL 与实测 SQL 都解析成结构件，逐项比覆盖率：

```
tables → join_keys → columns → predicates → structure
```

代价是三处假阳性，全是"结果对但诊断报差异"逼出来的：

| 假阳性 | 为什么不该算差异 |
|---|---|
| `uses_cte` 不同 | 扁平写法与预聚合写法可以给出完全一致的结果 |
| CTE 之间的 join | 那是查询内部的逻辑连接，不是物理关联 |
| 谓词只收顶层 | `year = 2024` 写在 CTE 里还是外层，是写法差异 |

修完后 10 条金标：**诊断结论与结果比对完全一致**（0 假阳、0 假阴）。

## 九、这段经历真正教我的三件事

1. **先有判据，再谈优化。** 没有结果比对，前面所有"优化"都不知道有没有用。
2. **抓到 bug 不等于归因正确。** 我的第一判断（扇出）自信、合理、且有代码佐证——但它是错的。**去查数据，别查记忆。**
3. **修复要验证在最难的路径上。** 单轮通过不代表多轮通过；默认路径和开关路径是两条流水线。
