## 这份题库怎么用

题库本身已经给了「考察点 / 开口怎么答 / 回答框架 / 面试官追问 / 避坑」五段式，结构很好。但它给的是**通用正确答案**，而面试真正拉开差距的是第二层：**你有没有一个具体项目，能把这条答案钉在地上。**

所以这篇的写法是：题干保留题库原意，答案换成**我自己项目里的证据**——两个项目（RAGent 检索运行时、ReportAgent Agent 运行时）里出现过的真实数字、真实失败、真实取舍。凡是我和题库说法不一致的地方，我会写清为什么不一致。

## Q1 · 什么是 Agent，跟普通 LLM 应用本质区别在哪（1.1）

**题库考察点**：基础概念、认知边界。

**开口版**：区别不在"用没用 LLM"，在**决策权在谁手里**。普通应用里流程是人写死的、LLM 只做生成；Agent 里 LLM 参与决策——调哪个工具、下一步做什么——形成"感知-决策-行动-观察"的闭环。所以判断一个系统是不是 Agent，我只看一句话：**有没有哪一步走哪条路由模型决定，而不是代码决定。**

**项目证据**：我的 ReportAgent 里，LLM 只在两个位置真正做决策——意图兜底分类、SQL 生成与修复；其余全是 workflow（需求卡校验、六道 SQL 安全闸、三态评估、报告渲染）。我把它叫"Agentic where uncertainty exists, deterministic where correctness matters"：**该决策的地方交给模型，该正确的地方交给代码**。

**追问「那 RAG 算 Agent 吗」**：不算，RAG 是能力模块。我的 RAGent 里也有意图路由和查询改写，但我不会管它叫 Agent——因为它没有"根据观察决定下一步行动"的循环。

## Q2 · 长任务里上下文怎么管理才不丢信息（1.5）

**题库考察点**：上下文工程、长程记忆。

**开口版**：分层存、按需取。窗口里只放当前几步，长期放外部存储，需要时检索回填；历史上长先压缩，但压缩只影响"给模型看的那一段"，原始流水永远不删。

**项目证据**：

| 层 | 实现 |
|---|---|
| 状态对象 | 状态拆成 5 块（请求/需求/执行/报告/运行），各有唯一写者 |
| 转录 | `conversations` 追加式，**只追加不改写** |
| 压缩 | 按 token 预算做滚动摘要，冷启动保留最近 K 轮原文 |
| 落盘 | 每个任务版本写一条 revision，带 before/after 的 `changes` |

**追问「状态对象为什么比纯文本稳」**：因为可检查。文本里模型说"我已经查过了"，你无法验证；状态对象里那句话对应一个字段，代码可以断言它是否真的被写过。

**追问「压缩会不会丢关键信息」**：会，所以要能回查。我们的压缩产物只是"注入用的视图"，一旦模型说"按刚才那样"，代码去原始转录里对齐，而不是让它从摘要里回忆。

## Q3 · 什么时候该让 Agent 自主，什么时候收住（1.6）

**题库考察点**：可控性权衡、场景判断。题库给的三轴是"风险 / 可逆性 / 确定性需求"，我完全同意，补一个第四轴。

**开口版**：前三条是常规——读操作放开、写操作加确认、不可逆的必须人工。我补第四条：**结果需要可复现的场景，连"看起来无害"的步骤也要收。**

**项目证据**：报表场景属于"结果必须可复现"，所以我们做的是**双闸**：

- **前置闸**：能判的先判（关键词 → 字典 → 才模型）。1427 轮里 **64% 完全不调模型**；
- **后置闸**：模型输出必须过枚举 / 注册表 / schema 白名单，再被确定性规则二次裁决。

举个真例：用户说「2024年各区域销售额排名」，模型漏抽时间，代码侧必须能从原话把 `2024年` 补回来——**这不是"给模型更多自主"，而是"不该让模型决定这个"**。

**追问「收太紧会不会变成死板 workflow」**：分界线是"歧义在哪"。歧义在理解（这句话要什么），给模型；歧义在正确性（这个数对不对），给代码。

## Q4 · 循环 / 幻觉 / 卡死怎么排查（1.7）

**题库考察点**：故障排查、实战经验。

**开口版**：三类现象都靠埋点和回放，不靠猜。而排查的前提是——**失败必须留下证据**。

**项目证据**：这一条我是被坑出来的。早期失败时系统不落库，结果：

- 前端只能一直转圈；
- 想知道模型生成了什么 SQL，只能翻日志；
- 用户侧完全看不到"失败了"。

所以后来定死：**SQL 三态（SUCCESS / EMPTY / FAILED）全部落一条 `report_version`**，FAILED 那条带 `error_kind` 和**尝试过的 SQL 原文**。

另外两个真实故障模式值得单列：

| 现象 | 真因 | 教训 |
|---|---|---|
| 字段死活传不到下游，逻辑看着都对 | 图的状态 schema 没声明该键，框架**静默丢弃** | "没报错但没生效"比报错难查十倍 |
| 数字差 3.4 倍，第一判断是 join 扇出 | 实际是数据跨四年而 SQL 无年份过滤 | 归因必须查数据，不能查记忆 |

**追问「怎么防循环」**：重试预算写死（SQL 修复 2 / MCP 2 / LLM 2），并且区分"可修"与"修不好"——权限不足重试一百次也没用。

## Q5 · 自研 vs 开源框架怎么权衡（2.2）

**题库考察点**：从团队、成本、可控性做工程决策。

**开口版**：题库的一句话很准——看团队要为哪个环节付"认知税"。我的补充是：**只把"不是差异化"的部分交给框架。**

**项目证据**：

| 用了 | 没用 |
|---|---|
| LangGraph 的**图/状态机**（节点编排、checkpoint） | 它的 Agent 抽象、预置 tool-calling agent |
| FastAPI / SQLAlchemy / pgvector | 自建向量库（没必要） |
| Hexo（这个博客） | 自研静态站 |

反过来，下面这些我全部自己写，因为它们就是项目的差异化：**需求卡契约、SQL 六道闸、三态落库、记忆准入与整合、执行准确率评测、子任务诊断**。这些没有任何框架能替你做对。

**追问「自研成本怎么控」**：靠"每层可单独评测"。RAG 的召回（hit@k）和 Agent 的执行准确率是两套指标，分开测才能知道该修哪层。

## Q6 · RAG 评估：召回率之外看什么（3.4）

**题库考察点**：覆盖检索、生成、端到端的多维评估。

**开口版**：题库的三层（检索质量 / 生成忠实度 / 端到端成功率）是对的。我要加一条更硬的：**先量一下召回的头上还有没有空间。**

**项目证据**：我做过 8 组 retrieval-only 消融，结果是——

| 指标 | 结果 |
|---|---|
| hit@10（8 组全部） | **1.000** |
| MRR | Baseline 0.842 → 全开 0.850（+0.8pp，噪声内） |
| 延迟 | 567–670ms（策略 hook 几乎不影响） |

**召回已经到天花板了。** 这时候继续在检索上优化是浪费，钱应该花在生成和端到端。同期的真增益来自"权威表格定向补充"：A 类 56.7% → **83.3%**，B 类 61.1% → **94.4%**。

还有一条关于裁判的：**错误拒答判 0 分**。RAG 里"检索到了却拒答"是最容易被指标放过的坏行为——看起来安全，实际是失败。

**追问「LLM 评委怎么防走过场」**：能用确定性方法判的绝不给 judge（比如数字比对），judge 只判"表述是否切题"。

## Q7 · MCP 解决了什么，和 Function Call 什么关系（4.3）

**题库考察点**：MCP 的架构定位与协议层差异。

**开口版**：不是替代关系，是**位置不同**。Function Call 解决"模型怎么表达要调一个工具"；MCP 解决"工具怎么被统一接进来"——它把工具/数据从具体宿主里解耦，站在更靠基础设施的位置。

**项目证据**：我两个项目之间真的用 MCP 连了一层。RAGent 里跑一个独立的 stdio MCP 服务，做数据字典：

```
PG 自省 → 确定性 Markdown 渲染 → 入 KB → 暴露 search_faq / search_tables
```

ReportAgent 侧作为 MCP client 连上去，把这两个工具注册进自己的工具表。这样"指标口径"这种知识**不需要塞进 Agent 的 prompt，也不需要 Agent 自己维护索引**。

**追问「为什么只用 stdio」**：因为两个进程在同一台机器上，stdio 最简单也最安全（不需要暴露端口、不需要额外鉴权）。要跨机器才考虑 SSE / Streamable HTTP。

**追问「MCP 会带来什么新问题」**：失败语义。我们定死一条：**工具失败必须显式返回不可用，不许返回空数组假装"没有结果"**——空数组会被下游当成"确实没有"，然后自信地答错。

## Q8 · 什么时候该上多智能体，什么时候是过度设计（5.1）

**题库考察点**：从任务可分解性、上下文隔离、并行收益三个维度判断。

**开口版**：题库的三条我认，我的默认答案是**不上**。判断标准是：多出来那层协作，换来了什么可测量的东西？换不来就别上。

**项目证据**：ReportAgent 里是**两张图**而不是多个 Agent：需求图产出卡片，执行图产出数据。它是"两阶段串行"，不是多智能体——因为第二阶段强依赖第一阶段的产物（卡片），拆成两个 Agent 只会多一轮消息传递。

真值得拆的信号在我看来只有三个：

1. 子任务**真的异构**（一个做检索、一个写代码，工具集完全不同）；
2. 单上下文**装不下**（两个任务互相污染 prompt）；
3. 能**真正并行**且收益可测（延迟从 X 降到 Y）。

**追问「那你为什么用 LangGraph 的图」**：图是编排手段，不是 Agent 数量。我用的是一张图里的节点，节点之间是确定性边。

## Q9 · 短期 / 工作 / 长期记忆怎么分（6.1）

**题库考察点**：记忆分层模型与各自取舍。

**开口版**：分层的判据不是"重不重要"，而是**"这句话多久还算数"**。我按生命周期分四层。

**项目证据**：

| 层 | 存什么 | 生命周期 |
|---|---|---|
| 长期表 | 稳定偏好与业务事实 | 无限期（用户级） |
| 工作区 | 候选 + 会话级偏好 | 会话 TTL 24h |
| 查询模板 | 成功 SQL + 向量 | 随访问热度衰减 |
| 转录 | 多轮对话 | 追加式不改写 |

两个关键设计：

- **准入闸**：靠措辞判期限（「以后/默认」→ 长期；「这次/先」→ 会话；没有标记 → 候选），再拦掉任务参数、指示引用、问句、碎片；
- **槽位键**：长期表的唯一键是 `(user_id, memory_key)`，`memory_key` 是意图槽位（`pref:chart` / `fact:<指纹>`）——所以**同一维度物理上不可能有两条矛盾记忆**，冲突写法走 UPSERT 覆盖。

**追问「记忆系统最容易出什么问题」**：不是"忘了"，是**"记错了"**。所以我们的默认是宁可不记。

## Q10 · 延迟优化：流式 / 并行 / 缓存（7.1）

**题库考察点**：从链路角度降低端到端延迟。

**开口版**：先把延迟拆开量一遍，再决定优化什么。我的经验是——**大多数 Agent 的延迟大头是"串行 LLM 调用次数"，不是单次模型慢。**

**项目证据**：单轮报表请求的实测预算（p50）：

| 阶段 | p50 | 占比 |
|---|---|---|
| 意图分类 | 2.4s（只有 36% 的轮次需要） | 6% |
| 需求理解 | 9.3s | 24% |
| SQL 计划 + 生成 | 7.0 + 7.7s | 38% |
| 报告规划 + 组装 | 6.4 + 5.8s | 32% |
| **合计** | **≈ 38.6s** | |

所以优化顺序是：**① 砍调用次数**（能用规则判的不调模型 → 意图层已省掉 64%）→ ② 合并相邻调用（SQL 计划与生成对简单查询可确定性拼装）→ ③ 流式与缓存。

流式这块我们做了：思考链与回答分两条流推、后台任务断连继续跑完并落库、前端靠会话快照恢复真实状态。

**追问「流式会不会掩盖真实耗时」**：会。首字延迟好看，总耗时没变。所以要分开量 p50 与 p95 的总耗时，而不是只看首字。

## Q11 · 用 LLM 评 LLM 的坑（7.3）

**题库考察点**：LLM-as-judge 的偏差来源与缓解。

**开口版**：偏差主要有三类——位置偏差（爱选第一个）、长度偏差（爱选长的）、以及**自偏好**（爱选跟自己风格像的）。但比这些更致命的是：**用 judge 去评一件本来可以客观判定的事。**

**项目证据**：我给评测做的第一刀不是加 judge，而是**把"结果对不对"从 judge 手里拿走**。

- 报告类任务有金标 SQL，执行结果直接比对：行按多重集、数值带容差、`NULL ≠ 空串 ≠ 0`；
- 只有"表述是否切题"这种真正需要语义判断的，才给 judge；
- judge 用 3 分制 rubric（每档有文字标准），并且**错误拒答判 0 分**。

**追问「你怎么知道 judge 本身可靠」**：抽查一致率 + 固定 rubric。但更根本的是：**如果一件事能被确定性判定，就不该让 judge 有话语权。**

## Q12 · 为什么用 LangGraph，有什么缺点，是不是过度设计（大厂真题）

**题库考察点**：框架选型的判断力（这题几乎必问）。

**开口版**：我用的只是它的**图 + 状态**，没要它的 Agent 抽象。缺点有三个，我都踩过；至于过度设计——取决于你是否真的有多个节点和分支。

**缺点（都是实感）**：

1. **状态静默丢键**：只有声明过的键会被传递。没声明的字段"不报错但不生效"，极难查；
2. **调试不如裸代码直观**：一层装饰器包住节点，栈追踪要绕一下；
3. **版本演进快**：早期 API 变动频繁，升级要读 changelog。

**为什么在我这儿不算过度设计**：因为有 12+ 个节点、有并行分支、有失败重试与条件路由，还要 checkpoint 恢复。如果只有一条线性流程，我会直接写几个函数，不套图。

**追问「那你会推荐别人用吗」**：会，但前提是想清楚"状态契约"。我的建议是：**先把状态拆块、每块的写者定下来，再上框架**——顺序反了就会变成"框架驱动架构"。

## 最后：一份自检清单

把这 12 题压缩成 6 个问题，面试前自问一遍就够了：

1. 我的系统里**哪一步**是模型决定的？（答不出 = 不是 Agent）
2. 我的**失败路径**长什么样，留了什么证据？（答不出 = 没做过生产）
3. 我有没有一个**换了就变差**的数字？（答不出 = 没评测）
4. 我砍掉过什么功能，为什么？（答不出 = 没做过取舍）
5. 我知道自己的**边界**在哪吗？（数据规模、并发、成本）
6. 同样的需求，重做一次我会**改哪三个决定**？

> 题库给的是骨架，项目给的是血肉。只有骨架的回答，面试官听三句就知道了。
