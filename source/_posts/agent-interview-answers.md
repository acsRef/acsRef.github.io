## 怎么读这篇

这篇文章有两个来源：

- **第一部分（Q1–Q12）**：来自 Agent 面试题库，覆盖最高频的 12 个考点；
- **第二部分（D1–D10）**：面试官顺着你的简历往下问时会问的**项目题**。题库里没有，但更容易翻车。

每题固定五段：

| 段 | 作用 |
|---|---|
| **一句话答案** | 开口第一句，20 秒内说完，先给判断 |
| **概念展开** | 把机制讲清楚（学习用，面试不一定要全说） |
| **项目里怎么做** | 具体到表 / 字段 / 数字，这是"真做过"的证据 |
| **追问与坑** | 面试官会往哪追，以及我踩过的坑 |
| **边界** | 我**没做**的部分。主动说，比被问出来强 |

文末有**术语速查**，卡住时回头看。

## Q1 · 什么是 Agent，跟普通 LLM 应用本质区别在哪（1.1）

**一句话答案**：区别不在"用没用大模型"，在**决策权在谁手里**——普通应用里流程是人写死的、模型只填空；Agent 里模型参与"下一步做什么"的决策，形成"感知 → 决策 → 行动 → 观察"的闭环。

**概念展开**：

- 一个可以自己检查的判据：**把模型换成 if-else，还能跑吗？** 能，说明模型只是填空（workflow）；不能，说明路由靠模型（agent）。
- 三个要件：会推理的模型、能调的工具、能存状态的内存。少一个就退化：缺内存 → 每轮失忆；缺工具 → 只能聊天。
- 自主程度是**光谱**，不是二元。从"固定流程里嵌一次模型判断"，到"完全自治的多智能体"，中间全是 Agent。

**项目里怎么做**：我的 ReportAgent 里，模型只出现在两个位置——

| 位置 | 模型做什么 | 为什么必须是模型 |
|---|---|---|
| 意图分类兜底 | 关键词和字典都判不出时，判断是闲聊 / 接口 / 报表 | 自然语言边界模糊 |
| SQL 生成与修复 | 把需求卡翻译成 SQL | 组合爆炸，写不出规则 |

其余全是 workflow：卡片校验、六道 SQL 安全闸、三态评估、报告渲染、记忆准入。所以它的定位是"**受控 Agent**"——决策点很少，但每个决策点后面都有一道确定性复核。

**追问与坑**：

- *「用了 Function Call 就算 Agent 吗？」* 不算。工具是能力，不是决策循环。一个"你问一句它查一次库"的机器人，是带工具的问答，不是 Agent。
- *「RAG 算 Agent 吗？」* 不算，RAG 是能力模块。我的 RAGent 里有意图路由和查询改写，但没有"根据观察决定下一步"的循环，我不叫它 Agent。
- 坑：**别用框架名当答案**（"我们用 LangChain 搭了个 Agent"）。追问一句"那你的决策点在哪"就空了。

**边界**：我们这个系统**不做开放式规划**（不会自己决定"先查 A 再查 B"）。它是单轮目标导向的分析 Agent，不是研究型 Agent。

## Q2 · 长任务里上下文怎么管理，信息才不会丢（1.5）

**一句话答案**：**分层存、按需取**。窗口里只放当前几步；历史放外部存储；压缩只影响"给模型看的那一段"，原始记录永远不删。

**概念展开**：新手最常见的错误是把三样东西混在同一个 prompt 里——

| 东西 | 特性 | 正确做法 |
|---|---|---|
| **状态**（任务进度、已填槽位） | 需要被代码读写和断言 | 结构化对象（JSON/dict），代码维护 |
| **转录**（用户和系统说过的话） | 只增不改，是审计与回溯的真源 | 落库，追加式 |
| **注入视图**（这一轮给模型看的上下文） | 每轮临时拼，可以裁可以压 | 由前两者生成，用完即弃 |

混在一起的后果：模型说"我已经查过了"，你无法验证（那只是文本）；压缩时把原始事实一起压掉，再也找不回来。

**项目里怎么做**：

| 层 | 实现 |
|---|---|
| 状态 | 拆成 5 块（请求 / 需求 / 执行 / 报告 / 运行），每块有唯一写者 |
| 转录 | `app.conversations` 追加式，**不改写** |
| 压缩 | token 预算 + 滚动摘要；冷启动保留最近 K 轮原文 |
| 审计 | 每个任务版本写一条 revision，带 `changes` 的 before/after |
| 恢复 | dev 用内存 checkpoint，非 dev 用 PG checkpoint（重启不丢） |

关键细节：压缩产物只是"注入视图"。模型说"按刚才那样再来一次"时，代码去**原始转录**里对齐，而不是让它从摘要里回忆。

**追问与坑**：

- *「状态对象为什么比纯文本稳？」* 因为可断言。文本里"我已经确认过了"无法验证；状态里那句话对应一个字段，代码可以检查它是否真的被写过。
- *「压缩丢了关键信息怎么办？」* 两件事：压缩前把结构化槽位（实体 / 决定 / 未决项）先落库；丢弃后仍能从原始转录回查。
- 坑：**只压缩不落库**。压完就没有源了，后面想查都查不到。

**边界**：我们没有做"对话向量化召回"（把历史对话做 embedding 检索）。长期记忆走结构化表 + 槽位键，不是向量。理由：对话流水里大部分是过程噪音，向量召回它反而引入噪声。

## Q3 · 什么时候该让 Agent 自主，什么时候收住（1.6）

**一句话答案**：题库给的三轴（风险 / 可逆性 / 可复现需求）都对，我再加第四轴——**看歧义在哪**：歧义在"理解"就交给模型，歧义在"正确性"就交给代码。

**概念展开**：

| 轴 | 松 | 紧 |
|---|---|---|
| 风险 | 读操作（查 / 搜 / 算） | 写操作、资金、权限 → 必须人工 |
| 可逆性 | 能回滚 | 不可回滚 |
| 可复现 | 一次性探索 | 合规报表、审计口径 |
| **歧义位置（补）** | "这句话想要什么" | "这个数对不对" |

第四轴最容易被忽略。SQL 生成本身是"理解"，但**生成的 SQL 能不能跑、结果对不对**是"正确性"——后者不该让模型拍板。

**项目里怎么做**：我们做的是**双闸**：

1. **前置闸（省成本）**：关键词 → 字典 → 才模型。1427 次报表轮次里，**64% 完全不调模型**；
2. **后置闸（保正确）**：模型输出必须过 ① 枚举白名单 ② 指标注册表 ③ schema 字段白名单，再被确定性规则二次裁决（时间 / 范围 / 口径从原话回填）。

再加两道"物理约束"：SQL 六道安全闸（只读 / 关键字 / AST / 危险函数 / 表白名单 / EXPLAIN）+ 独立只读数据库角色；重试预算写死（SQL 修复 2 / MCP 2 / LLM 2）。

**追问与坑**：

- *「收这么紧会不会变成死板 workflow？」* 分界线就是第四轴：判断"要什么"给模型，判断"对不对"给代码。
- *「怎么证明收紧了没伤体验？」* 要算**误路由率**（本该走模型却被规则拦掉的占比）。说实话：**这个指标我现在没有**，是已知缺口（见 D8）。
- 坑：靠 prompt 让模型"不要瞎写 SQL"。实测无效——我们真的见过模型把用户明说的"2024年"丢掉。

**边界**：没有 HITL 审批流（个人项目），只有"确认卡片"这一道人工确认。

## Q4 · 循环 / 幻觉 / 卡死怎么排查（1.7）

**一句话答案**：先让失败**留下证据**，再谈排查。三类现象都靠埋点 + 回放，不靠猜。

**概念展开**：把三类现象对到三种信号上——

| 现象 | 典型信号 | 处理方向 |
|---|---|---|
| 循环 | trace 里同一 Action 重复出现 | 最大步数 + 明确的"已完成"判据 |
| 幻觉 | 最终答案里有工具没返回过的内容 | 强制引用 + 事实校验 |
| 卡死 | 某一步耗时无限增长 / 异常被吞 | 超时 + 严格参数校验 + 降级 |

共同前提：**每一步都要有 span**（谁、多久、输入输出是什么）。没有 span，只能凭记忆复盘。

**项目里怎么做**：

- **三态落库**：SQL 结果是 `SUCCESS / EMPTY / FAILED` 三态，**三种都写一条报告版本**。FAILED 那条带 `error_kind` 和**尝试过的 SQL 原文**。
- **trace 双 sink**：PG（本地可查）+ Langfuse（可选），span 记录节点级耗时与输出。
- **错误分类两张表**：同一个错误，对 Agent 是"能否修复"，对用户是"能否重试"，分开写。

真实故障两个，都值得讲：

1. **字段静默丢失**：图的状态 schema 没声明某个键，框架直接丢掉，不报错。表现是"逻辑都对，值传不到下游"。查了很久。
2. **3.4 倍偏差误归因**：看到数字差 3.4 倍，我判断是 1:N join 扇出（理由看起来非常充分），去查真库才发现每单支付恒为 1 条、数据其实是四年——真因是需求层丢了年份。**归因要查数据，不能查记忆。**

**追问与坑**：

- *「循环怎么防？」* 预算是硬约束，同时区分"可修"与"修不好"——权限不足重试一百次也没用。我们只有 syntax / object_not_found 进修复，permission / timeout 直接 fail。
- *「幻觉怎么验？」* 报告只允许引用查询结果（三层 validator：结构、数值来源、禁止自由生成）。insight 文案不做正则审计（那是另一种自欺）。

**边界**：没有自动 bad case 聚类（靠人工把线上失败用例补进评测集）。

## Q5 · 自研 vs 开源框架怎么权衡（2.2）

**一句话答案**：题库那句"看团队要为哪个环节付认知税"很准。我的补充是——**只把"不是差异化"的部分交给框架**。

**概念展开**：把系统切成三类，分别决策：

| 类别 | 例子 | 选择 |
|---|---|---|
| 通用编排 | 图 / 状态机 / 重试 | 用框架（LangGraph） |
| 通用设施 | Web 框架、ORM、向量库 | 用开源（FastAPI / SQLAlchemy / pgvector） |
| **差异化能力** | 需求卡契约、SQL 安全闸、评测判据、记忆准入 | **自研** |

第三类如果也用框架，你就没有项目可言了——面试官问"你的贡献是什么"，只能答"我配置得比较好"。

**项目里怎么做**：

| 用了 | 没用 |
|---|---|
| LangGraph 的**图 + 状态 + checkpoint** | 它的 Agent 抽象、预置 tool-calling agent |
| FastAPI / SQLAlchemy / pgvector | 自建向量数据库（没必要） |

自研清单（项目的"内脏"）：需求卡与槽位契约、六道 SQL 闸、三态落库、记忆准入与整合、执行准确率评测、子任务诊断。

**追问与坑**：

- *「自研维护成本怎么控？」* 靠**每层可独立评测**。RAG 的 hit@k 和 Agent 的执行准确率是两套指标，分开测才知道该修哪层。
- 坑：把"我写了多少行"当卖点。行数不是能力，**可验证性**才是。

**边界**：没有 fork 改造开源框架（那要长期跟进 upstream，个人项目不划算）。

## Q6 · RAG 评估：召回率之外看什么（3.4）

**一句话答案**：题库的三层（检索质量 / 生成忠实度 / 端到端）都对。但我先做一件它没提的事——**量一下召回还有没有空间**。

**概念展开**：为什么"召回率高"会骗人：

- `recall@10 = 1.000` 意味着**每一题的答案块都在前 10 里**。这时候再优化检索，指标不会动了——因为**没有可提升的空间**。
- 真正的失败这时发生在下游：块都在，但排序不好（MRR 低）、或者模型没用上（忠实度低）、或者拒答了。

所以指标的用法是**先定位瓶颈层，再优化**，而不是每层都堆指标。

**项目里怎么做**（RAGent 实测）：

| 指标 | 8 组配置（20 题回归集） |
|---|---|
| hit@10 | **全部 = 1.000** |
| MRR | Baseline **0.842** → 5 策略全开 **0.850**（+0.8pp，噪声内） |
| 延迟 | 567–670ms（策略 hook 几乎不影响） |

结论：**检索层到天花板了**，5 个高级策略（跨文档关联 / 权威 section 加权 / section 补充 / 跨年补充 / 查询拆解 / 证据门）全部默认关闭，代码保留作单点复评。

同期真增益来自"权威表格定向补充"（表格数据在 BM25 里得分低、常被挤出 top-K）：A 类 **56.7% → 83.3%**，B 类 **61.1% → 94.4%**。

> 说明：这两个百分比来自项目当时的评测产物记录，没有在最新代码上重跑。

再加一条裁判规则：**错误拒答判 0 分**。RAG 里"检索到了却拒答"最容易被放过——看起来安全，实际是失败。

**追问与坑**：

- *「LLM 评委怎么防走过场？」* 能用确定性方法判的绝不给 judge（数字比对）。judge 只判"表述是否切题"。
- *「评测路径和生产路径一致吗？」* 血泪：我们的 `/retrieve` 端点**绕过了** pipeline 里的 evidence gate，而生产走 `/chat/stream`。所以那两行 gate 的数值测的不是 gate 生效的路径。**任何"评测脚本直调内部函数"都有这个风险。**

**边界**：跨文档 / 多跳检索只做了开关，没上线（消融证明无增益）。

## Q7 · MCP 解决了什么，和 Function Call 什么关系（4.3）

**一句话答案**：不是替代，是**位置不同**。Function Call 解决"模型怎么表达要调一个工具"；MCP 解决"工具怎么被统一接进来"——它站在更靠基础设施的位置。

**概念展开**：

| | Function Call | MCP |
|---|---|---|
| 是什么 | 模型输出结构化调用请求（JSON Schema） | 一套协议（JSON-RPC 2.0），把工具 / 数据从宿主解耦 |
| 谁解析 | 宿主程序 | MCP Client |
| transport | 无（就是一次 API 调用的参数） | stdio / SSE / Streamable HTTP |
| 原语 | 只有"函数" | Tools（可调用）/ Resources（只读上下文）/ Prompts（模板） |

一句话记法：**Function Call 是"点菜的说法"，MCP 是"厨房怎么连起来"。**

**项目里怎么做**：我两个项目之间真用了一层 MCP。RAGent 里跑一个独立 stdio 服务做数据字典：

```
PG 自省 → 确定性 Markdown 渲染 → 上传到 KB → 暴露 search_faq / search_tables
```

ReportAgent 作为 MCP client 连上去，把这两个工具注册进自己的工具表。于是"指标口径"这种知识**不需要塞进 Agent 的 prompt，也不需要 Agent 自己建索引**。

一个比协议更重要的工程约定：**工具失败必须显式不可用，不许返回空数组假装"没有结果"。**

```
❌ 检索失败 → []            # 下游会当成"知识库里确实没有" → 自信地答错
✅ 检索失败 → unavailable   # 下游决定 retry / clarify / fail
```

**追问与坑**：

- *「为什么只用 stdio？」* 两个进程同机，stdio 最简单也最安全（不开端口、不额外鉴权）。跨机才考虑 SSE / HTTP。
- 坑：把 MCP 当"更高级的 Function Call"讲。位置讲错，后面全错。

**边界**：只用了 Tools 原语，没用 Resources / Prompts；没做远程 transport 与鉴权。

## Q8 · 什么时候该上多智能体（5.1）

**一句话答案**：**默认不上**。判断标准只有一句：多出来那层协作，换来了什么**可测量**的收益？说不出来就别上。

**概念展开**：题库给了三条判据，我认同，并补上它的代价侧：

| 判据 | 成立才值得拆 | 代价 |
|---|---|---|
| 任务**异构** | 子任务工具集 / 系统提示完全不同 | 每轮多几次消息传递 → token 与延迟翻倍 |
| 上下文**必须隔离** | 两个任务互相污染 prompt | 共享状态要额外做对齐与仲裁 |
| 能**真正并行** | 延迟可从 X 降到 Y（可测） | 失败从线性变网状，定位极难 |

第三种最容易骗自己：写"并行"很容易，**证明它真的更快**很难（依赖同步、结果合并、重试往往把收益吃回去）。

**项目里怎么做**：ReportAgent 里是**两张图**（需求图 / 执行图），不是多个 Agent。因为第二阶段强依赖第一阶段的产物（需求卡）——把它拆成两个 Agent 只会多一轮消息传递，没有任何收益。

真要拆，我会按"异构"拆：检索（RAGent）和 SQL 执行（ReportAgent）已经是两个进程了，它们之间用 MCP 而非消息总线——**同步 RPC 比异步消息更适合这种"必须等结果才能继续"的依赖**。

**追问与坑**：

- *「那你为什么用 LangGraph 的图？」* 图是编排手段，不是 Agent 数量。一张图里 12 个节点，节点间是确定性边。
- 坑：为了显得高级硬拆多智能体。面试官一问"拆完延迟变多少"就露了。

**边界**：没有做多智能体编排（GroupChat / 角色分工那些），因为不认为这个场景有收益。

## Q9 · 短期 / 工作 / 长期记忆怎么分（6.1）

**一句话答案**：分层的判据不是"重不重要"，而是**"这句话多久还算数"**。我按生命周期分四层。

**概念展开**：

| 层 | 例子 | 生命周期 | 为什么单独一层 |
|---|---|---|---|
| 上下文窗口 | 当前几步、当前卡片 | 一轮 | 零检索成本，但最贵、掉线即失 |
| 工作区（候选） | "这次先用表格" | 会话 24h | 还没确定要不要长期留 |
| 长期库 | "以后都用柱状图" | 无限期 | 跨会话生效 |
| 历史流 | 完整对话与执行记录 | 追加式 | 审计与回溯真源 |

**项目里怎么做**：

| 机制 | 实现 |
|---|---|
| 准入闸 | 靠措辞判期限：「以后 / 默认」→ 长期；「这次 / 先」→ 会话；无标记 → 候选；再拦掉任务参数 / 指示引用 / 问句 / 碎片 |
| 唯一键 | `(user_id, memory_key)`，`memory_key` 是**意图槽位**（`pref:chart` / `fact:<指纹>`） |
| 冲突 | 同槽位 UPSERT 覆盖（`revision+1`，旧值留 `previous_content`）——结构上不可能两条矛盾并存 |
| 推断晋级 | 同一说法观察到 ≥3 次 → 晋级 active，但 confidence **封顶 medium**；`high` 只留给用户明说 |
| 判定移出热路径 | 晋级 / 过期 / 同维度收敛由每日跑批（CLI）完成，在线只读写 |

**追问与坑**：

- *「记忆系统最容易出什么问题？」* 不是"忘了"，是**"记错了"**。所以默认宁可不记。
- 坑：只看过一次的推断就当事实用。我们的规则是封顶 medium，且必须在卡片上能看到"按了什么口径"。

**边界**：没有用户画像（性格 / 长期偏好建模），也没有跨用户学习。

## Q10 · 延迟优化：流式 / 并行 / 缓存（7.1）

**一句话答案**：先把延迟**拆开量一遍**。大多数 Agent 的延迟大头是"**串行 LLM 调用次数**"，不是"单次模型慢"。

**概念展开**：一个 Agent 请求的耗时 ≈ Σ(每次 LLM 调用) + Σ(工具) + 编排开销。所以优化优先级是：

1. **砍次数**（能确定性判的不调模型）——收益最大、风险最低；
2. **合并相邻调用**（两个调用能不能合成一次）；
3. **流式 / 并行 / 缓存**（改善体验或削峰，但不减少总工作量）。

**项目里怎么做**：一次真实请求 38.6 秒，花在哪看这张图（颜色=可优化的地方）：

![延迟预算瀑布](/img/diagrams/latency-budget.svg)

| 阶段 | p50 | p95 | 占比 |
|---|---|---|---|
| 意图分类 | 2.4s（只有 36% 轮次需要） | 5.8s | 6% |
| 需求理解 | 9.3s | 17.1s | 24% |
| SQL 计划 | 7.0s | 16.6s | — |
| SQL 生成 | 7.7s | 31.2s | 38%（两段合计） |
| 报告规划 | 6.4s | 28.8s | — |
| 报告组装 | 5.8s | 8.4s | 32%（两段合计） |
| **合计** | **≈ 38.6s** | | |

注意两件事：

- 六步**全是串行**，因为后一步依赖前一步的产物。所以"并行"在这里基本没有用武之地——**真正的杠杆是减少步数**。
- **p95 和 p50 差很多**（SQL 生成 7.7s vs 31.2s）。说明长尾来自重试 / 超时，不是平均变慢。优化长尾要单独做（超时预算、降级）。

**已经做的**：意图层用规则吃掉 64% 的轮次（不调模型）；思考链与回答分两条流推（体验）；后台任务断连继续跑完并落库（不阻塞用户）；前端靠会话快照恢复真实状态。

**还没做的（下一步）**：单指标 + 卡片维度 + 时间过滤这类简单查询，**SQL 计划可以用注册表的 `expr / joins` 确定性拼装**，直接省掉 7.0s。但要动架构边界，得单独评审。

**追问与坑**：

- *「流式会不会掩盖真实耗时？」* 会。首字延迟好看，总耗时没变。所以要**分开量首字与总耗时**。
- *「缓存什么？」* 我们缓存的是"查询模板"（成功 SQL + 向量），不是答案——数据会变，答案不能缓存。
- 坑：只说"我们上了流式"。那不是优化延迟，是优化感知。

**边界**：没做语义缓存、没做并行工具调用（本场景没有可并行的独立工具）。

## Q11 · 用 LLM 评 LLM 的坑（7.3）

**一句话答案**：常见偏差是位置、长度、自偏好。但比这些更致命的是——**用 judge 去评一件本来可以客观判定的事**。

**概念展开**：

| 偏差 | 表现 | 缓解 |
|---|---|---|
| 位置偏差 | 总选第一个 / 最后一个 | 交换顺序重跑，看结论是否稳定 |
| 长度偏差 | 偏爱长答案 | rubric 里明确"简洁"档，或截断后评 |
| 自偏好 | 偏爱和自己风格像的 | 换一个不同家族的模型当裁判 |
| **越权** | 让 judge 判"数字对不对" | **根本不该给 judge 这个权力** |

**项目里怎么做**：我给评测做的第一刀，是把"结果对不对"从 judge 手里拿走：

- 报告类任务有**金标 SQL**，评测时现跑（跟着数据走），结果直接比对：行按多重集、数值带 Decimal 容差、`NULL ≠ 空串 ≠ 0`；
- judge 只判"表述是否切题"，用 **3 分制 rubric**（每档有文字标准，不让它给 1–10 分）；
- **错误拒答判 0 分**；
- 数字类问题用确定性校验辅助，不经过 judge。

**追问与坑**：

- *「judge 自己可靠吗？」* 抽查一致率 + 固定 rubric。但更根本的是"能确定性判的不要给它话语权"。
- 坑：拿 judge 当唯一指标。你会得到一条好看的曲线，和一堆错的数字。

**边界**：没有建 judge 校准集（同一批样本人工标注 vs judge 打分的偏差统计）。这是可以补的下一步。

## Q12 · 为什么用 LangGraph，有什么缺点，是不是过度设计（大厂真题）

**一句话答案**：我只用它的**图 + 状态 + checkpoint**，不用它的 Agent 抽象。缺点有三个，我都踩过；是不是过度设计，取决于你**是否真的有多个节点和分支**。

**概念展开**：选编排框架前先问三个问题：

1. 我的流程是线性的，还是有分支 / 重试 / 回环？
2. 我需要"断点续跑 / 恢复"吗？
3. 我的状态需要被多个节点共享并且可断言吗？

三个都"是"，才值得上图；只有一个"是"，写函数更省事。

**项目里怎么做**：12+ 个节点、有并行分支、有条件路由（校验失败 → 修复 → 回生成）、需要 checkpoint 恢复。**所以不算过度设计。**

**三个缺点（都是实感）**：

| 缺点 | 表现 | 应对 |
|---|---|---|
| 状态静默丢键 | 没在 schema 声明的键**不报错但不传递** | 先把状态契约写清，再上框架 |
| 调试不直观 | 节点被装饰器包住，栈追踪要绕 | 关键节点打结构化日志 + span |
| 版本演进快 | 早期 API 变动频繁 | 只用稳定子集（图 / 状态 / checkpoint） |

**追问与坑**：

- *「换掉它要多少成本？」* 节点都是纯函数，换编排层是机械工作；贵的不是框架，是**状态契约**——那部分跟框架无关。
- 坑：把"用了 LangGraph"当答案。反问"它的 checkpoint 你怎么用的"就露了。

**边界**：没有深入 subgraph / interrupt 高级特性（只有 legacy 澄清节点用了 `interrupt`）。

# 第二部分 · 项目深挖 10 题（题库没有，但更容易翻车）

> 这部分是面试官拿着你的简历问的。每题给出"我会怎么答"，并标出**哪里必须诚实**。

## D1 · 为什么拆两张图，而不是一张？

**一句话**：因为"理解需求"和"执行查询"的**失败语义完全不同**，混在一起就没法归因。

**展开**：

| | 需求图 | 执行图 |
|---|---|---|
| 产出 | 需求卡（契约） | 数据 + 报告版本 |
| 失败意味着 | 没听懂 / 该澄清 | SQL 错 / 数据没有 |
| 成本 | 几次 LLM | 几次 LLM + 真实 SQL |
| 是否可反复 | 用户改一次就跑一次 | 确认后才跑 |

拆开带来三个直接好处：**确认前不花 SQL 成本**；失败能立刻分层归因；卡改了只需重跑执行图。

**诚实边界**：代价是多一次状态传递与两套入口，代码量增加。

## D2 · 你说的"确定性裁决"到底裁决什么？

**一句话**：裁决的是"**用户已经说出口的字面事实**"，不是替用户做新决定。

| 规则 | 输入 | 输出 |
|---|---|---|
| 时间 | 原话「2024年7月」 | 卡片 `time_range = 2024年7月` |
| 范围 | 原话「华东」 | 卡片 `scope = [华东]` |
| 口径 | 原话命中注册表 | 覆盖模型猜的口径 |
| 期限 | 「以后」/「这次」 | 记忆写长期库 / 会话库 |

**关键细节**：只在字段**为空**时回填，模型给了一律尊重。

**为什么必须做**：实测模型会漏抽用户明写的时间，于是 SQL 没有年份过滤，把四年数据一起算——金标 96,318,061.74 vs 实测 326,102,457.72。

> 完整版（12 行真实输入→输出表 + 四条设计约束 + 差分探针抓到的 4 类差异）见 [项目深挖（二）：确定性裁决](/posts/deepdive-deterministic-adjudication/)。

## D3 · 执行准确率怎么保证金标是对的？

**一句话**：金标**用 SQL 表达，不写死数字**——评测时用只读角色现跑，所以它跟着数据走，不会因为数据更新而失效。

| 做法 | 原因 |
|---|---|
| 金标是 SQL 而非具体数字 | 数据一变，写死的数字立刻失效 |
| 与生产同一套安全闸 | 金标不能走另一条数据库访问路径 |
| 比对是纯函数 | 可单测、可离线复算，不必跑整批 |
| 产物里同时落 `sql` 与 `golden_sql` | 结果可自证，不用回数据库翻 |

**诚实边界**：我第一次的归因是错的（判成 join 扇出），但**金标本身是对的**——错的是我对差异的解释。

## D4 · 20 条 case 只标了 10 条，为什么？

**一句话**：剩下 10 条**不该有金标**，硬标等于自欺。

| 类别 | 条数 | 为什么不标 |
|---|---|---|
| 澄清 / 闲聊 / 检索 / 安全 | 7 | 没有 SQL 结果可比 |
| 故障注入 | 1 | 判据是 verdict 与错误码 |
| 语义多解 | 1 | 「再按产品细分」有两种合理读法，写死等于替产品决定 |
| 明细（LIMIT） | 1 | 排序并列时行集不确定，金标会随实现漂移 |

**追问「那覆盖不就低了？」** 低，但有理由：**这 10 条每条都在抓 bug**（铺金标过程中抓出 3 个真缺陷）。20/20 全绿但理由是"照抄被测 SQL"才是真的低。

## D5 · 三态落库的代价是什么？

**一句话**：写放大和前端复杂度，换来"失败可见、可追溯"。

- 写放大：失败也写一条版本（含 `error_kind` 与尝试过的 SQL）；
- 前端要处理三态渲染（错误带 / 空数据带 / 正常报告）；
- 好处：用户不会"转圈到超时"，排查时能直接看到模型生成了什么。

**诚实边界**：三态是靠"约定"保证的，没有数据库层约束强制——有人绕过持久化函数直接写，仍可能漏。**能用约束保证的别靠约定**，这是可改进点。

## D6 · 记忆冲突怎么解？为什么不用余弦相似度合并？

**一句话**：用**结构槽位**解冲突（同槽位 UPSERT），不用向量合并——因为向量在这个任务上**不可分**。

真 embedding 实测：

| 关系 | 相似度区间 |
|---|---|
| 同义（该合并） | 0.695 – 0.933 |
| 不同的事（不该合并） | 0.642 – **0.950** |
| 相反说法（绝对不能合并） | **0.906 – 0.962** |

**三类完全重叠**。取 θ=0.90：7 个误并、8 个误拆。

改成结构优先判定器（极性 → 数字 → 原子冲突 → 原子值一致 → 灰区复审 → distinct），同一批 26 对：**错误合并 0、精确率 1.00、召回 0.92**。

**一句话经验**：**当你打算用相似度做判断，先去量"你不想合并的那类东西"的相似度。** 重叠就换信号，别调阈值。

> 完整版（26 行实测数据 + 2 处漏并根因 + 判定流程图）见 [项目深挖（一）：记忆冲突与归并](/posts/deepdive-memory-merge/)。

## D7 · 你的 schema 只有 7 张业务表，怎么证明能扩展？

**一句话**：我不能用它证明"企业级"，但可以证明"**换一套 schema 不需要改代码**"。

三处设计是数据驱动的：

| 层 | 数据源 |
|---|---|
| 指标口径（表达式 + 依赖 join） | `metrics.yaml` |
| 维度 / 时间桶 / 字段提示 | `schema_hints.yaml` |
| 表结构 | 运行时从 MCP 自省，不进代码 |

所以换一套星型模型，理论上只改 yaml。

**诚实边界**：**这是设计意图，不是已证明的结论**——我只在一套 schema 上跑过。而且 7 张表意味着"100% 成功率"没有说服力，我从不拿它当企业级证据。

## D8 · 64% 规则命中率怎么算的？误路由率多少？

**一句话**：命中率是数出来的（1427 轮里 508 轮调了意图 LLM）；**误路由率我没有**——这是已知缺口。

命中率 = 1 − 508/1427 ≈ 64%，数据来自 LLM 调用记录。

误路由率需要"本该走模型却被规则拦掉"的标注，而我**没有逐轮记录用户原话与判定结果**，所以算不出来。

**下一步**：把每轮 `user_query` 记进任务 revision（现在只记归并后的状态），才能离线回放，算出命中率 / 误路由率。

**这句话本身就是加分项**：能说清"我的指标缺哪一半、怎么补"。

## D9 · 六道 SQL 闸里，哪一道最关键？

**一句话**：**EXPLAIN 与只读角色**。前几道是静态检查，会漏；后两道是"真跑一遍才知道"。

| 层 | 能拦什么 | 漏什么 |
|---|---|---|
| 只读 / 关键字 / AST | 明显写操作与语法 | 合法但危险的函数 |
| 危险函数黑名单 | 文件读取、网络、睡眠 | 名单外的新函数（白名单式更稳） |
| 表白名单 | 越权访问系统表 | 拼错的表名（这时靠 EXPLAIN） |
| **EXPLAIN** | 数据库自己说不行 | 运行期超时（靠 statement_timeout） |
| **只读角色** | 任何写操作 | 读越权（靠表 / 列权限） |

原则：**不要指望一层拦住所有事，要让漏掉的那层由下一层兜住。**

## D10 · 这个项目最难的三个决定是什么？

1. **指标从"跑通率"换成"结果准确率"**：它否掉了我之前所有"优化有效"的自信——跑通率 1.0，答案能错 3.4 倍。
2. **记忆不用向量合并，改结构判定**：在真数据上先测，把第一方案否掉。
3. **接受"覆盖率 10/20"而不是凑满**：承认有些 case 不该判，比让全绿好看更重要。

共同点：三个决定都是**放弃一种"看起来更好"的做法**，换一种"能被验证"的做法。

# 第三部分 · 术语速查

| 术语 | 一句话解释 |
|---|---|
| **hit@k / recall@k** | 前 k 个结果里是否包含答案 / 覆盖了几成答案块 |
| **MRR** | 第一个正确结果的排名取倒数再平均；越接近 1 说明正确结果越靠前 |
| **RRF** | 按"排名"融合多路召回（`Σ 1/(k+rank)`），不需要三路分数可比 |
| **cross-encoder 重排** | 把 query 和候选块拼一起过模型；比向量内积准但慢，所以只对 top-N 做 |
| **MMR** | 去冗余：既看相关性也看"和已选结果有多像"，避免同一事实取两遍 |
| **扇出（fan-out）** | 一对多 join 把行复制，导致 SUM 被放大——典型的"跑对了但数错了" |
| **幂等** | 同一操作执行多次，结果和执行一次一样（重试安全的前提） |
| **熔断** | 失败到阈值就暂时不再调它，避免拖垮整条链路 |
| **多重集比较** | 不看行顺序，但重复行要按数量对得上 |
| **p50 / p95** | 一半请求快于它 / 95% 请求快于它；长尾看 p95，别只看平均 |
| **token 预算** | 给一段上下文或一次生成设上限，超了就压缩或截断 |
| **确定性裁决** | 用代码规则覆盖模型输出里"用户已经明说的事实" |

| 评测判据 | `execution_accuracy` + `task_decomposition` + 金标 SQL | Evaluator v1（15 题门禁 + 65 题基准 + judge rubric） |
| 指标口径注册表 | `app/knowledge/metrics.yaml` | —（RAG 侧没有指标口径概念） |

1. 我的系统里**哪一步**是模型决定的？（答不出 = 不是 Agent）
