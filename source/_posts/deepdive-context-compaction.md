有人连着问我三个问题：

1. **什么时候自动压缩上下文？**
2. **有没有手动压缩？**
3. **如果正在执行任务的时候上下文满了怎么办？**

我第一反应是「有」——毕竟代码里有 `RECENT_WINDOW`、`L2 digest`、`L2.5 归档`、token budget，看起来都齐。但第二个问题我答不出来：**手动入口在哪？** 界面上没有，API 里也没有。第三个问题更糟：我知道有 `MAX_TASK_DURATION` 兜底，但「窗口真的满了会怎么样」，我没试过。

于是我先做了一件不写代码的事：**查现状**。

## 一、这套东西从来没跑过

真库查出来（65 个会话、415 条消息）：

```
digest 非空       = 0 行
mid_digest 非空   = 0 行
单会话最多真实消息 = 8 条（最大 143 字符）
消息正文均值       = text 13 字 / assistant_text 28 字
```

压缩阈值是「消息数 > 20」——所以**所谓 L2 摘要，一条都没生成过**。它是一段为不存在的规模写的代码。

顺手读代码还找到三个真缺陷：

| # | 缺陷 | 后果 |
|---|---|---|
| ① | 装配层预算用 `text[:char_cap]` 截字符串 | 对话按时间正序在尾部，一超预算就**留最老、丢最新**，正好和「保尾」相反 |
| ② | 摘要 LLM 一抛错，`ContextRuntime.build()` 整块抛 → 调用点 `try/except` 吞掉 | 对话上下文**连同记忆召回一起变空**，且 `digest_msg_count` 不推进，下一轮继续炸 |
| ③ | 需求侧规定「宁可超预算也不丢数字」，执行侧 prompt 却写着「不含数值」 | 两套标准打架，而执行侧恰好是最需要数字的那一侧 |

## 二、去读 DSH 的压缩实现

我没打算重新发明，先读了 DeepSeek Harness 的 `@deepseek-ai/dsh-compaction` 家族源码（4 个包：抽象接缝 / 默认后端 / 无模型剪裁 / `/compact` 命令）。它的骨架是：

```text
measure   → tokenMeter 量出当前 surface 的 token
trigger   → min(窗口×0.8, 窗口−预留输出−headroom)  三个触发：每步压力 / 换模型 / provider 报溢出
select    → 从尾部往回攒 retainTokens（≈16% 预算），压缩它之前的一切；绝不切开 tool-call/result 配对
summarize → 固定 8 段结构化模板（Primary Request / Key Technical Concepts / Files and Code / …）
guard     → 摘要必须比被替换内容更小才提交；异步期间 surface 变了就 abort
commit    → compaction/start（锁）→ summary → user/message(replace) → compaction/end
```

两个细节我印象很深：

- **摘要调用复用 KV cache**：它把会话原有的 system、tools、消息原样重放一遍，只把「压缩指令」挂在最后一条 user 消息上——这样这次辅助调用是上一次请求的**真前缀**，暖缓存能命中。
- **日志式 bracket 就是锁**：`compaction/start` 在让出 CPU 之前就落盘；任何失败都只尝试写一次 `compaction/end`；崩在中间留下孤立的 start，本身就是「有人在压」的信号。

我照着读，也照着改。但有一处必须动。

## 三、我要改的那一处：数据不参与压缩

DSH 是靠 prompt 要求模型「把数字抄对」。可对数据分析 Agent 来说，数值是**业务事实**——抄错等于篡改。而且这个项目已经吃过一次亏：模型写的散文摘要把错口径逐轮固化下来，后来专门把需求侧的压缩改成「宁可超预算，数字一条不丢」。

所以我把它拆成两条通道：

![对话压缩的双通道：叙述走模型，数据走确定性抽取](/img/diagrams/compaction-dual-channel.svg)

- **叙述通道**：交给模型写成 5 段 checkpoint（用户目标 / 已确认口径 / 用户纠正 / 已否决的写法 / 未完成事项），段位固定、不许增删；
- **数据通道**：日期、月份、年份、金额、百分比、订单号由确定性正则从被折叠区间**逐字**抽出来，写进 `<数据事实>` 块——**不经过任何模型**。

那模型能不能在 checkpoint 里写数字？能引用，但**每一个数字都得在数据事实里逐字存在**：

```python
def numbers_not_in_facts(summary: str, facts_text: str) -> list[str]:
    allowed = numeric_tokens(facts_text)          # 事实块里的数值 token 集合
    return [t for t in numeric_tokens(summary)    # 自己算的 / 四舍五入的 → 不在集合里
            if t not in allowed
            and not any(_same_number(t, o) for o in allowed)]   # 20 与 20.0 视为同一个数
```

判越界怎么办？**退回确定性骨架**：每行只留开头 24 个字，数字只从事实块取。这比「让模型自由发挥」安全，也比「干脆不压缩」诚实。

第一版我写的是「禁止出现任何阿拉伯数字」——实测立刻被打脸：模型写「最高是 11 月」，这是**正确且必要**的引用，却被我一刀切判成越界，于是整轮降级。**一刀切的规则通常说明你还没想清楚要防什么**：要防的是「改写」，不是「引用」。

## 四、真数据、真流程：62%，以及三个合成用例抓不到的缺陷

合成用例能证明算法边界，但证明不了「真跑起来会不会丢东西」。所以我又写了一个 env-gated 的真流程测试：

| 环节 | 用什么 |
|---|---|
| 数据 | **现查数仓**：2024 华东 9631.81 万元、华南 5206.83 万元、月度 Top2、真实订单 80889、真实同比 20.0% |
| 会话 | 40 轮真实形态（少量取数 + 大量口径/维度/格式讨论），每轮按生产链路落一条 `turn_trace` 过程行 |
| 入口 | `ContextRuntime().build(agent="confirmed_execution_sql_agent")`，真 recall + 真压缩 + `digest` 真落库 |
| 下游 | 真 `sql_graph._plan` 做差分：压缩上下文 vs 全量原文 |
| 失败 | 真 `LLMAdapter` + 打不通的 base_url（不是 mock 抛异常） |

结果：

```
[checkpoint] LLM 结构化（5 段齐）
[数字对账] 越界数字 = []
[体积] 原文 2352 字 ≈ 1171 tokens → 压缩后 876 字 ≈ 440 tokens   ← 降 62%
[滚动] digest_msg_count 105 → 111
[plan/压缩] time_range='2024'   metric='净销售额' dims=['月份','区域']
[plan/原文] time_range='2024'   metric='净销售额' dims=['月份','区域']   ← 语义等价
[短会话] 4 轮/8 条：digest=无                                    ← 双闸不触发，一个字不动
[降级] 模式=骨架折法，上下文非空                                  ← 真实 adapter 打不通
```

**但这轮测试最有价值的产出不是这个 62%，是它抓出的三个缺陷**——合成用例一个都抓不到：

1. **裸月份不被保护**：对话里说「最高是 **11 月**」，折叠后这个月份彻底消失（checkpoint 又不许编数字）→ 用户再问「最高那个月」，上下文里什么都没有。补 `\d{1,2}[月日号]`。
2. **裸年份不被保护**：「先看 **2024 年**华东」的年份消失——旧规则认为年份由结构化 `time_range` 承载，那是**需求侧**的前提，执行侧摘要里根本没有那张卡。补 `\d{4}[-/年]`。
3. **折叠反而变大**：确定性折法给每行追加「（数据：…）」，与 `<数据事实>` 重复，实测**压缩后 258 tokens > 原文 204**。压缩成膨胀——于是加了最后一道「净收益守门」：渲染结果 ≥ 原文就本轮放弃。

第 3 条顺带解释了为什么必须有「放弃」这个选项：**压缩不是必须发生的事**。

## 五、执行中窗口满了怎么办

之前这里是空的：provider 报窗口超限时，`_classify_retryable` 不认它（它不是瞬时故障，重试必然复现），于是重试 2 次白等，然后整条任务失败。

按 DSH 的第三触发补上：捕获溢出 → 强制全量折叠（`retain=0`，只留最近一问一答）→ 重建上下文 → **只重试一次**。

真正值钱的是这一步的实测——我构造了一个 36 万字符的 prompt，让 provider 自己报错：

```
Error code: 400 - {'code': 20015, 'message': 'number of input tokens (210003)
 has exceeded max_seq_len (163840) limit.'}
```

我第一版词表写的是 `context_length_exceeded` / `maximum context length` / `context window`——**一个都没命中**。SiliconFlow 的文案是 `max_seq_len`。补上之后：溢出 → `True`，坏 key 的 401 → `False`（不误判）。

端到端也跑了真错误：

```
context overflow in sql agent (session=...): ...; forcing full compaction, retry once
→ 最终抛出 BadRequestError，总共调了 2 次
```

2 次 = 第一次溢出 → 压缩 → 重试一次仍溢出 → 抛。**不做压缩风暴**。

## 六、估算比例错了 1.79 倍

上面那句报错还免费送了一个数据点：21 万 tokens 对应 36 万字符 → 1.71 字/token。而我们的估算器一直按 **3 字/token** 算。

我干脆正式测了一遍（读 provider 的 `usage.prompt_tokens`）：

| 样本 | 字符 | 实测 tokens | 字/token |
|---|---|---|---|
| 中文散文 | 5 000 | 2 992 | **1.67** |
| 中文散文 | 100 000 | 59 797 | **1.67**（5k→100k 稳定） |
| 中文 + 数据/SQL | 5 000 | 2 011 | 2.49 |
| 纯英文 | 5 000 | 887 | 5.64 |

**旧估算把中文低估 1.79 倍**：它认为 15.7 万字是 52 428 tokens，实际已经 9.3 万。现在没出事，只是因为 provider 硬上限 163 840 兜着——一旦把窗口调大，就会在「自以为还有余量」的时候直接撞墙。

改成 CJK 感知：`ceil(CJK/1.67 + 其余/3.0)`，误差从 0.79 倍收到 0.94~1.00 倍。顺手把 `.env` 的窗口从 65 536 调到 **131 072**（距 163 840 留 3.2 万给输出与误差）：可容纳从约 10.9 万字变成 **约 21.9 万字**，压缩阈值从 8.8 万字抬到 **17.5 万字**。

## 七、界面：一个按钮，和一句实话

手动压缩原来只有 API。现在工作台画布头部有个「整理上下文」：

![工作台头部的「整理上下文」按钮与 toast：已整理上下文 4808 → 1451 字](/img/posts/compact-ui.png)

Playwright 真机点了一次：

```
button disabled? false
toast = 已整理上下文：4808 → 1451 字
console errors = 0
```

关键不是按钮，是**文案不许假装成功**。后端可能什么都不压，`reason` 有四种：

| reason | 界面说的话 |
|---|---|
| `ALREADY_COMPACTED` | 这个会话的上下文已经整理过了 |
| `NOTHING_TO_COMPACT` | 这段对话还很短，不需要整理 |
| `NOT_WORTH_IT` | 整理不划算（摘要不会比原文更短），已保持原样 |
| `EMPTY_SESSION` | 这个会话还没有对话内容 |

同一套「别白花钱」的闸也用在自动路径上：**收益上界闸**（上限 = 原文 − 尾部 − 数据块，太小就直接跳过、不调 LLM）+ **拒绝记忆**（同一会话同一边界判过「不值得」，10 分钟内不再试）。否则短消息会话会每轮白调一次模型、再放弃。

## 八、我决定不做的

- **日志式 surface 替换 / `compaction/start|end` 锁**：消息表 + `report_version` 已经是 append-only 事实源，LangGraph checkpoint 存的是图状态不是对话；再加一套 shadow + replay 只是重复造轮子。
- **tool-pair 边界**：对话表只有 `text` / `assistant_text`，没有 tool 消息。它的对应物是**一问一答**——折叠不许切开一轮问答，因为「只留问、不留答」比不折叠更有害。
- **给 requirement / report 节点接溢出恢复**：那两条链的 prompt 规模远小于窗口，没有证据表明会撞上。**不写无证据的机制。**
- **`/compact` 命令行**：没有命令面板，按钮就够。

## 九、一句话

以前我以为「压缩」是「把历史变短」。这轮做完，我觉得它真正在做的是：

> **分清哪些东西可以被缩短，哪些一旦缩短就不再是它自己了。**

对话的措辞可以被缩短——「用户先问了华东、后来改成华南、明确否决了环比」压成五行就够了。但 `9631.81 万元` 不能被缩短成 `9631 万元`，那一刻它就不是那个数了。

数字由脚本搬，叙述由模型写，两者的边界用守卫钉死——这大概就是我在这套压缩里想说明的全部。
